# Day 19 — Конспект: композиция MCP-инструментов

## 1. Что такое композиция инструментов

Один инструмент делает одно дело. Композиция — когда несколько инструментов
соединяются в цепочку, где **выход одного становится входом следующего**:

```
search → summarize → save_to_file
```

Ключ к композиции — **явные контракты**: каждый инструмент принимает и возвращает
понятные типы (`dict` с известными полями). Тогда звенья стыкуются без «магии» и
цепочку можно проверить по частям.

## 2. MCP — это pull-модель

MCP-сервер не может сам «толкнуть» агенту промежуточный результат. Поэтому
цепочку собирают двумя способами:

1. **Агент** вызывает инструменты по очереди (гибко, но зависит от LLM);
2. **Сервер** отдаёт составной инструмент, который выполняет всю цепочку внутри.

Здесь есть оба: три отдельных инструмента (`search`, `summarize`,
`save_to_file`) и составной `pipeline`, который вызывает их сам. Второй вариант и
есть «автоматическое выполнение цепочки».

## 3. Получение данных — `search_api.search`

Ходит в Wikipedia Search API (`action=query&list=search`), без ключа. Возвращает:

```python
{"query": "...", "results": [{"title", "url", "snippet"}]}
```

Тонкость: `snippet` приходит с HTML (`<span class="searchmatch">…</span>`), его
чистит `_strip_html`. Ошибки сети/пустого ответа → `SearchError`, которую
`server.py` превращает в `ValueError` (MCP покажет это как ошибку, а не падение).

## 4. Обработка — `summarizer.summarize`

Экстрактивная суммаризация (без LLM):

1. текст режется на предложения;
2. считается частотность «значимых» слов (длина ≥ 3, без стоп-слов);
3. предложение оценивается суммой частот слов, делённой на длину;
4. берётся топ-N, но возвращаются они **в исходном порядке** — так саммари
   читается связно.

Это чистая функция: ни сети, ни файлов — поэтому её легко и приятно тестировать.

## 5. Сохранение — `storage.save_to_file`

Пишет контент **как есть** в UTF-8, возвращает `{path, bytes_written,
written_at}`. Каталог `out/` создаётся автоматически. Разделение обязанностей:
`storage` только пишет; заголовок и структуру markdown собирает `pipeline`.

## 6. Композиция — `pipeline.run`

Связывает три этапа и возвращает **отчёт о передаче данных**:

```python
{
  "query": "...",
  "stages": {
    "search":    {"result_count": 5, "top_titles": [...]},
    "summarize": {"sentence_count": 2, "summary_chars": 53},
    "save":      {"path": "...", "bytes_written": 487},
  },
  "output_path": "...",
  "summary": "...",
}
```

Именно `stages` доказывают «корректность передачи»: видно, сколько данных пришло
на вход каждого этапа и что вышло наружу.

## 7. MCP-обёртка — `server.py`

`MCPServer("compose")` + декоратор `@mcp.tool()`. Каждая функция дублирует
контракт модуля и конвертирует доменную ошибку в `ValueError`. В opencode
инструменты видны с префиксом: `compose_pipeline` и т.д.

## 8. Как проверить

- `pytest -q` → 18 офлайн-тестов (суммаризатор, storage, поиск с моком, пайплайн
  с моком, stdio).
- Живьём: `pipeline.run('Model Context Protocol')` → отчёт + файл в `day19/out/`.
- В opencode: «Найди… и сохрани конспект» → одна фраза, цепочка из трёх
  инструментов, готовый файл.

## Упражнения

1. Добавить инструмент `translate` между `summarize` и `save_to_file`.
2. Ограничить `pipeline` числом источников (`limit`).
3. Сохранять ещё и сырые результаты `search` рядом с конспектом (JSON).
