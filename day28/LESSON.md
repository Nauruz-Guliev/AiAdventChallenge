# День 28 — RAG на локальной LLM (урок)

До этого RAG (Дни 21–25) работал с облачным DeepSeek, а локальная модель (Дни 26–27) отвечала
без базы. День 28 соединяет их: **и поиск, и генерация — локально**, а облако остаётся только
как «вторая модель» для сравнения и как судья.

Главный тезис: **качество RAG = качество поиска**, а локальная модель уже умеет отвечать по
контексту. Поэтому retrieval (эмбеддинги + индекс) мы не меняем — переиспользуем Неделю 6.

## 1. Два «локально»

- **Локальный retrieval** — модель эмбеддингов `paraphrase-multilingual-MiniLM-L12-v2`
  лежит на диске и считается на CPU/GPU. Никаких API.
- **Локальная генерация** — `gemma4:12b` через Ollama (`localhost:11434`).

Оба компонента не зависят от интернета. Наружу уходит только трафик Telegram.

## 2. Конвейер

```
вопрос ─► embed ─► top-30 ─► реранк ─► фильтр(min_sim) ─► top-6 ─┬─► gating(>=0.60)
                                                                  └─► prompt(context[n])
                                                                        └─► gemma4:12b
                                                                              └─► ответ + источники
```

**Реранк** (из Дня 24) подмешивает к cosine-оценке лексическое пересечение с вопросом — так
наверх поднимаются чанки, где реально встречаются слова запроса. **Фильтр** отбрасывает слабые
чанки, **gating** отказывается отвечать, если лучший чанк слишком далёк от вопроса («не нашёл»).

## 3. Промпт и источники

Системный промпт просит помечать факты ссылкой `[n]` на блок контекста. После генерации бот:

- показывает блок «📚 Источники» — для каждого `[n]` печатает `source :: section (score)`;
- извлекает **цитаты** — самую длинную общую подстроку между ответом и текстом чанка (LCS,
  из Дня 24); «grounded» цитатой считается фрагмент длиной ≥ 24 символов.

## 4. Сравнение с облаком — `/compare` и `/eval`

Сравнивать честно можно, только если **контекст одинаковый**: поэтому retrieval выполняется
один раз, а в локальную и облачную модель уходит один и тот же промпт. Разной остаётся
только генерация — это и есть предмет сравнения «локальная модель против облачной».

## 5. Слепой судья

Качество оценивает LLM-судья (DeepSeek) по рубрике 0…1. Важно, что судья **не знает**, какая
модель дала ответ (ему подают только вопрос, эталон и ответ) — иначе он бы подыгрывал «своим».
Судья возвращает JSON `{"score": …, "reason": …}`, который мы аккуратно парсим (с фолбэком на
первое число в тексте).

## 6. Что такое «скорость» и «стабильность»

- **Скорость** — средняя латентность запроса (мс). Для локальной модели ещё важен **tok/s**:
  Ollama возвращает `eval_count` и `eval_duration`, отсюда `tokens_per_second`.
- **Стабильность** — разброс метрик по прогонам: σ балла судьи (насколько «плавает» качество) и
  σ латентности (насколько «плавает» время), плюс доля ошибок/таймаутов. Один прогон ничего не
  говорит о стабильности — поэтому по умолчанию 3 прогона на вопрос.

## 7. Почему `think=false`

`gemma4:12b` — «думающая» модель. Для RAG контекст уже дан, а «размышления» тратят время и
раздувают латентность. По умолчанию thinking выключен (`/think on` включает) — так скорость
локальной модели честнее сопоставима с облачной.

## 8. Инженерные детали

- **Долгий `/eval`** — считается в фоновой задаче, прогресс пишется в сообщение («прогон: 3/30»),
  второй `/eval` в том же чате отклоняется (лок).
- **Сеть Telegram** — в этой сети `api.telegram.org` резолвится в заблокированный IP; решаем
  подменой IP на рабочий (`TELEGRAM_API_IP`) с сохранением SNI/сертификата, плюс polling
  переподключается при обрыве.
- **Один токен с Днём 27** — запускать оба бота одновременно нельзя.

## 9. Что почитать в коде

- `app/application/rag_service.py` — весь RAG-ход (retrieve → gate → generate).
- `app/application/benchmark.py` — прогон и агрегация метрик.
- `app/application/judge_deepseek.py` — слепой судья и разбор оценки.
- `app/presentation/handlers.py` — команды, кнопки и стриминг.
