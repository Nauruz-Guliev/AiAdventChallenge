# День 7: сохранение контекста

## Цель

Продолжить приложение из `day6` в отдельной папке `day7` и добавить сохранение контекста между запросами и перезапусками приложения.

Пользователь должен иметь возможность:

- создавать несколько независимых чатов;
- переключаться между чатами;
- видеть историю выбранного чата;
- перезапустить backend и продолжить разговор;
- отправить новый вопрос с учётом предыдущих сообщений.

`day6` не изменяется.

## Выбранный подход

История хранится в JSON-файле через отдельный repository. Это минимальное и прозрачное решение для учебного задания: формат можно открыть и показать, а persistence не зависит от внешней базы данных.

Альтернативы:

- SQLite был бы надёжнее для большого числа чатов и конкурентных записей, но добавил бы схему и лишнюю инфраструктуру.
- `localStorage` был бы проще для frontend, но не сделал бы backend-агент источником контекста и не демонстрировал бы серверное восстановление.

## Архитектура

`day7` создаётся как самостоятельная копия `day6`.

### Domain

`domain/models.py` расширяет `ChatMessage` ролями `system`, `user` и `assistant`. Также добавляются модели чата и ошибка `ChatNotFound`.

### Application

`application/ports/chat_repository.py` определяет контракт хранилища:

- создание чата;
- получение списка чатов;
- получение истории чата;
- сохранение пары сообщений.

`application/agent.py` получает `LLMGateway` и `ChatRepository`. Метод `run(chat_id, user_text)`:

1. проверяет пользовательский текст;
2. загружает историю выбранного чата;
3. добавляет system prompt и новый user message;
4. отправляет всю историю через `LLMGateway`;
5. после успешного ответа сохраняет user и assistant messages;
6. возвращает `AgentResult`.

### Infrastructure

`infrastructure/json_chat_repository.py` реализует repository и хранит данные в `day7/backend/data/chats.json`.

Запись выполняется через временный файл и замену исходного файла, чтобы процесс не оставил повреждённый JSON при сбое во время сохранения.

Путь к файлу должен быть конфигурируемым. Значение по умолчанию — `data/chats.json`.

### Presentation

FastAPI предоставляет четыре операции:

- `POST /api/chats` — создать чат;
- `GET /api/chats` — получить список чатов;
- `GET /api/chats/{chat_id}` — получить историю чата;
- `POST /api/chats/{chat_id}/messages` — отправить сообщение агенту.

Route не обращается к DeepSeek напрямую. Она вызывает `Agent`, а agent использует repository и gateway.

### Frontend

React загружает список чатов при старте, показывает боковую панель, позволяет создать новый чат и загружает историю выбранного чата. После отправки сообщения ответ добавляется в текущую ленту.

## Формат хранения

```json
{
  "version": 1,
  "chats": [
    {
      "id": "uuid",
      "title": "Что такое API?",
      "created_at": "2026-09-13T12:00:00Z",
      "updated_at": "2026-09-13T12:01:00Z",
      "messages": [
        {"role": "user", "content": "Что такое API?"},
        {"role": "assistant", "content": "API — это..."}
      ]
    }
  ]
}
```

System prompt не хранится. Agent добавляет его при каждом вызове, чтобы настройки поведения агента оставались актуальными.

Новый чат сохраняется сразу. Первый успешный вопрос становится заголовком, ограниченным примерно 50 символами. `updated_at` меняется после каждого успешного сообщения. История сохраняется только после успешного ответа LLM, поэтому ошибка провайдера не оставляет незавершённое сообщение пользователя.

## Поток запроса

```text
React
  -> FastAPI route
  -> Agent
  -> ChatRepository: загрузить историю
  -> LLMGateway: system + история + новый вопрос
  -> ChatRepository: сохранить user + assistant
  -> React
```

После перезапуска backend repository снова читает JSON с диска. Поэтому контекст не зависит от памяти процесса.

## Ошибки

- неизвестный `chat_id` возвращает `404`;
- пустое или слишком длинное сообщение возвращает `422`;
- ошибки DeepSeek используют существующие безопасные ответы `502`, `429` и `504`;
- повреждённый JSON не перезаписывается автоматически и приводит к безопасной серверной ошибке;
- ошибка записи истории не считается успешной отправкой сообщения.

## Проверка

Backend-тесты должны покрывать:

- создание, сохранение и повторную загрузку чата через `JsonChatRepository`;
- передачу предыдущих сообщений из Agent в gateway;
- сохранение контекста после создания нового экземпляра repository;
- API для создания, списка, загрузки чата и отправки сообщения;
- `404` для неизвестного чата.

Также выполняются frontend production build и ручной сценарий:

1. создать чат;
2. отправить `Меня зовут Анна`;
3. полностью перезапустить backend;
4. открыть тот же чат;
5. отправить `Как меня зовут?`;
6. убедиться, что агент учитывает ответ `Анна`.

Критерий готовности: сообщения сохраняются в JSON, чат восстанавливается после полного перезапуска, а новый запрос отправляется в LLM вместе с прежней историей.
