# День 6: Первый LLM-агент

## Цель

Создать отдельный учебный web-проект `day6`, который демонстрирует первого агента:

1. пользователь вводит запрос в web-интерфейсе;
2. backend принимает запрос;
3. отдельный класс `Agent` подготавливает и выполняет задачу;
4. агент обращается к DeepSeek API через абстракцию gateway;
5. ответ возвращается в React-интерфейс.

Главная цель задания — показать, что агент является отдельной сущностью, а вызов LLM не находится непосредственно в HTTP route.

## Границы проекта

- Новый проект располагается в `day6` и не изменяет реализацию предыдущих дней.
- Backend и вся предметная логика реализуются на Python.
- Web-интерфейс реализуется на React/Vite.
- Используется DeepSeek API через OpenAI-compatible Python SDK.
- Каждый запрос независим; история диалога не хранится.
- Используется модель `deepseek-chat`; её можно переопределить переменной `DEEPSEEK_MODEL`.
- DeepSeek API вызывается через `https://api.deepseek.com/v1`, если `DEEPSEEK_BASE_URL` не задан явно.
- API-ключ хранится только в `day6/backend/.env` и никогда не передаётся frontend.
- Streaming, авторизация пользователей, база данных и долговременная память агента не входят в первый этап.

## Выбранный подход

Используется FastAPI + Clean Architecture + React/Vite.

Почему:

- FastAPI даёт ясный HTTP-слой и удобную валидацию схем;
- Python остаётся основным языком backend и агента;
- Clean Architecture отделяет сценарий агента от транспорта и конкретного провайдера;
- React позволяет наглядно показать чат и прохождение запроса через компоненты;
- Vite сохраняет frontend простым и не требует полноценного frontend-фреймворка поверх React.

## Слои и ответственности

### Domain

Содержит простые модели результата и этапа выполнения. Не импортирует FastAPI, OpenAI SDK или React.

### Application

`Agent` — отдельный класс и основной use case проекта. Он получает `LLMGateway` через конструктор и предоставляет метод:

```text
run(user_text) -> AgentResult
```

`Agent` проверяет прикладные ограничения текста, формирует сообщения для LLM, вызывает gateway и собирает результат. Он не знает о HTTP, JSON и конкретном DeepSeek SDK.

### Ports

`LLMGateway` — Python-протокол с операцией завершения запроса. Он описывает, что нужно агенту от LLM, но не знает, как устроен конкретный провайдер.

### Infrastructure

`DeepSeekGateway` реализует `LLMGateway` с помощью OpenAI-compatible клиента и переменных окружения. Здесь находятся provider-specific настройки (`DEEPSEEK_API_KEY`, `DEEPSEEK_BASE_URL`, `DEEPSEEK_MODEL`), таймаут и перевод ошибок SDK в прикладные исключения.

### Presentation

FastAPI route принимает HTTP-запрос, валидирует Pydantic-схему, вызывает `Agent` и сериализует результат. Route не формирует prompt и не обращается к DeepSeek SDK напрямую.

### Frontend

React отвечает только за ввод, состояние запроса, отображение ответа, ошибки и визуализацию потока `UI → Agent → DeepSeek API → UI`. API-ключ и прямой URL провайдера frontend не видит.

## Поток данных

Frontend отправляет:

```http
POST /api/chat
Content-Type: application/json

{
  "message": "Объясни, что такое API простыми словами"
}
```

Далее выполняется цепочка:

```text
React UI
  → FastAPI route
  → Agent.run(message)
  → LLMGateway.complete(messages)
  → DeepSeek API
  → AgentResult
  → JSON response
  → React UI
```

Ответ endpoint имеет форму:

```json
{
  "answer": "API — это способ...",
  "model": "deepseek-chat",
  "duration_ms": 1840,
  "stages": [
    {"name": "UI", "status": "completed"},
    {"name": "Agent", "status": "completed"},
    {"name": "DeepSeek API", "status": "completed"}
  ]
}
```

Этапы являются безопасной учебной телеметрией. До ответа frontend показывает локальные состояния `pending` и `active`, а после ответа использует завершённые этапы из `AgentResult`. Это не streaming и не попытка измерить внутреннее выполнение провайдера. Этапы показывают прохождение запроса, но не раскрывают hidden chain-of-thought или внутренние рассуждения модели.

## Ошибки

- Пустое или слишком длинное сообщение: HTTP `422` и сообщение валидации.
- Неверный API-ключ: безопасное сообщение о проверке `.env`.
- Ограничение провайдера: сообщение о временной занятости и повторной попытке.
- Timeout или ошибка сети: сообщение о недоступности DeepSeek.
- Неожиданная ошибка: общее безопасное сообщение для пользователя и подробность только в серверном логе.

Ошибки инфраструктуры не должны протекать в React с секретами, stack trace или API-ключами.

## Интерфейс

Используется гибридный экран:

- основная область содержит текущий пользовательский запрос и ответ, без сохранения истории между запросами;
- боковая или нижняя область показывает `AgentFlow`;
- этапы визуально меняются из `pending` в `active`, затем в `completed` или `error`;
- во время запроса кнопка отправки блокируется;
- после ответа показываются модель и длительность запроса;
- на мобильном экране блоки складываются вертикально.

Визуальный приоритет: чат остаётся главным, а схема объясняет архитектуру рядом с ним.

## Тестирование

### Unit-тесты агента

`Agent` тестируется с `FakeLLMGateway`, поэтому тесты не используют сеть и API-ключ:

- текст передаётся gateway;
- ответ gateway возвращается пользователю;
- создаются ожидаемые этапы;
- ошибка gateway преобразуется в ожидаемую прикладную ошибку;
- Agent не зависит от DeepSeek SDK.

### API-тесты

FastAPI `TestClient` проверяет:

- успешный `POST /api/chat`;
- отклонение пустого сообщения;
- отклонение слишком длинного сообщения;
- безопасное преобразование ошибки провайдера;
- вызов Agent через dependency override.

### Frontend-проверки

Frontend должен:

- отправлять сообщение по кнопке и Enter;
- показывать переходы этапов;
- отображать ответ;
- отображать безопасную ошибку;
- блокировать повторную отправку во время запроса;
- корректно работать на desktop и mobile.

## Критерии готовности

- В репозитории есть отдельный `day6`.
- Класс `Agent` находится отдельно от FastAPI route и DeepSeek-клиента.
- Агент получает текст и возвращает ответ через gateway.
- React-интерфейс успешно отправляет запрос и показывает ответ.
- На экране видна схема `UI → Agent → DeepSeek API → UI`.
- API-ключ не попадает во frontend и Git.
- Unit- и API-тесты проходят без реального запроса к DeepSeek.
- README позволяет запустить проект и понять назначение каждого слоя.
