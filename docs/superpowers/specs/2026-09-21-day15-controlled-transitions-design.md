# День 15. Контролируемые переходы состояний

## Цель

Сделать жизненный цикл задачи явным и проверяемым: у задачи есть конечный
набор состояний и объявленная таблица разрешённых переходов; ассистент не
может перепрыгнуть этап; любая недопустимая попытка перехода фиксируется и
объясняется. День 15 — копия дня 14 с новой прослойкой контроля переходов.

## Требования задания

- у задачи — допустимые состояния;
- между ними — разрешённые переходы;
- ассистент не может перепрыгнуть этап (нельзя реализацию до утверждённого
  плана, нельзя финал без проверки);
- проверяются: попытки недопустимого перехода, реакция ассистента,
  корректность продолжения после паузы.

## Состояния

`Stage`: `planning` → `approval` → `execution` → `validation` → `done`.

Новая стадия `approval` («план на утверждении») отделяет предложенный план от
начала реализации. В `approval` модель не вызывается; реализация начинается
только после явного `approve_plan`.

## События и таблица переходов

События: `propose_plan`, `approve_plan`, `complete_step`, `complete_validation`.

```
ALLOWED_TRANSITIONS = {
    planning:   {approval},
    approval:   {execution},
    execution:  {execution, validation},
    validation: {done},
    done:       set(),
}
```

`transition(state, event, payload=None)` — единственный способ сменить стадию.
Недопустимое событие поднимает `InvalidTransitionError(event, from_stage,
allowed_events)`.

## Ассистент просит переход

Промпт каждого активного этапа требует структурированный ответ:

- `planning` → `{"event": "propose_plan", "steps": [...]}`;
- `execution` → `{"event": "complete_step", "result": "..."}`;
- `validation` → `{"event": "complete_validation", "report": "..."}`.

Парсер достаёт событие из ответа. Если JSON не найден, применяется текстовый
фолбэк: считается ожидаемое для этапа событие (поведение дня 14 сохраняется).
Если событие объявлено, но таблицей не разрешено (например `{"event":
"finish"}` на этапе `execution`), переход отклоняется.

## Гейт утверждения

При стадии `approval` эндпоинт сообщений возвращает уведомление «План ждёт
утверждения» и не двигает состояние. Выполнение стартует только по
`approve_plan` (кнопка «Утвердить план» / `POST /api/task/transition`).

## Журнал попыток и аннотация

`TaskState` хранит последние 5 отклонённых попыток
`{event, from_stage, to_stage, reason}` (в `to_dict`/`from_dict`). При
отклонении:

- состояние не меняется;
- ответ аннотируется: «⚠ Переход «execution → done» отклонён: сначала
  проверка. Ассистент возвращён к этапу «выполнение»»;
- попытка попадает в журнал.

## API

- `GET /api/task/transitions` — вся таблица переходов и подписи стадий.
- `POST /api/task/transition {event}` — единственная точка смены стадии.
  Недопустимое событие → 409 с причиной; попытка фиксируется. Переход при
  паузе → 409.
- `TaskStateResponse` дополняется `allowed_stages` и `rejections`.

## Пауза

`pause` — на любой стадии, кроме `done`; `resume` не меняет стадию и сохраняет
журнал. Пауза/продолжение на `approval` остаётся на `approval` (утверждение не
теряется и не проскакивается).

## Frontend

`TaskStatePanel`: пять стадий, строка «доступно: …», кнопка «Утвердить план» на
стадии `approval`, блок отклонённых переходов (золотой акцент). `App.jsx`:
`getTransitions`/`postTransition`, обновление задачи. Стиль дня 14, без
градиентов.

## Тесты

- домен: таблица, валидные/недопустимые переходы, журнал, гейт,
  пауза/продолжение на каждой стадии, roundtrip;
- агент/движок: нет плана → отклонение и аннотация; нет автозапуска
  реализации; попытка `finish` в `execution`; корректная цепочка;
- API: `GET transitions`, `POST transition` (ok / 409 / пауза),
  `send_message` в `approval`;
- `npm run build`.
