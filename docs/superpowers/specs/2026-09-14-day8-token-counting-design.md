# День 8: подсчёт токенов и лимит контекста

## Цель

Продолжить приложение из `day7` в отдельной папке `day8` и добавить в код агента подсчёт токенов:

- для текущего запроса пользователя;
- для всей истории диалога;
- для ответа модели.

Пользователь должен иметь возможность в UI сравнить:

- короткий диалог;
- длинный диалог;
- диалог, который превышает лимит контекста.

Приложение должно показать:

- как растут токены и оценка стоимости по мере диалога;
- что ломается при переполнении лимита.

`day7` не изменяется.

## Контекст и ограничения

Факты из официальной документации DeepSeek (api-docs.deepseek.com, сентябрь 2026):

- легаси-имя `deepseek-chat` обслуживается моделью `deepseek-flash` (DeepSeek-V4.1-Flash), поэтому ответы API приходят с `model=deepseek-flash`;
- реальный лимит контекста — 1M токенов, max output — 384K;
- цены `deepseek-flash` (peak): input cache miss $0.30 / 1M токенов, input cache hit $0.006 / 1M, output $1.20 / 1M.

Следствие: переполнить настоящий 1M-контекст из UI нереально (сотни долларов и часы времени). Поэтому в приложении вводится настраиваемый **бюджет контекста** `CONTEXT_LIMIT_TOKENS` (демо-дефолт 8000 токенов). Реальный лимит и вид настоящей ошибки API документируются в README.

## Выбранный подход

Два источника данных о токенах:

- **локальная оценка до отправки** — tiktoken (`cl100k_base`), приблизительно для DeepSeek; позволяет разделить «текущий запрос» и «историю» и предсказать переполнение;
- **точный `usage` из ответа API** — `prompt_tokens`, `completion_tokens`, `total_tokens`; сохраняется с каждой парой сообщений, поэтому накопительные токены и стоимость переживают рестарт.

Поведение при переполнении бюджета: честная ошибка + предупреждение заранее. Локальный pre-check считает токены до отправки; при превышении бюджета запрос к API не выполняется, сообщение не сохраняется в историю, UI показывает понятную ошибку. Автообрезка истории (sliding window) — out of scope.

Альтернативы:

- только `usage` из API — не разделить запрос и историю, нельзя предупредить заранее;
- только локальный подсчёт — числа расходятся с реальным биллингом;
- переполнение реального 1M-контекста — непрактично по стоимости и времени.

## Архитектура

`day8` создаётся как самостоятельная копия `day7` (свои `.venv`, `.env`, `data/chats.json`, порты backend 8000 / frontend 5173).

### Domain

`domain/models.py`:

- `TokenUsage(prompt_tokens, completion_tokens, total_tokens)` — точный usage из API;
- `ChatMessage` получает опциональное поле `usage: TokenUsage | None` (заполняется у assistant-сообщений);
- `AgentResult` получает поле `usage: UsageReport`;
- `UsageReport` — сводка одного хода: `request_tokens`, `history_tokens` (локальная оценка), `response_tokens`, `prompt_tokens_api`, `total_tokens_api` (точные из API), `dialog_total_tokens`, `dialog_cost_usd`, `context_limit`, `context_remaining`, `warning`;
- новое исключение `ContextLimitExceeded(estimated_tokens, context_limit)`.

### Application

`application/agent.py`, метод `run(chat_id, user_text)`:

1. проверяет пользовательский текст;
2. загружает историю чата;
3. локально считает `request_tokens` (новое сообщение) и `history_tokens` (system prompt + история);
4. если оценка превышает `CONTEXT_LIMIT_TOKENS` — бросает `ContextLimitExceeded` **до вызова gateway и без записи в историю**;
5. отправляет сообщения через `LLMGateway`;
6. после успешного ответа берёт точный `usage` из API, считает стоимость и накопительные итоги диалога (сумма usage по всем assistant-сообщениям истории + текущий ход);
7. сохраняет exchange с usage в repository;
8. возвращает `AgentResult` с `UsageReport` (`warning=True` при заполнении бюджета ≥ 80%).

Порт `ChatRepository.append_exchange` дополняется параметром `usage`.

### Infrastructure

`infrastructure/token_counter.py` (новый): `TokenCounter` на tiktoken с encoding `cl100k_base`, методы `count_text(text) -> int` и `count_messages(messages) -> int`. В docstring зафиксировать, что для DeepSeek это оценка.

`infrastructure/deepseek_gateway.py`:

- читает `completion.usage` и возвращает его в `LLMResponse.usage`;
- маппит настоящую ошибку API `400 context_length_exceeded` (`BadRequestError`) в `ContextLimitExceeded` как предохранитель.

`infrastructure/json_chat_repository.py`: сериализует `usage` assistant-сообщений в JSON и восстанавливает обратно. Старые файлы без поля `usage` читаются как `None`.

`infrastructure/settings.py`: `CONTEXT_LIMIT_TOKENS` (по умолчанию 8000), цены `INPUT_PRICE_PER_MILLION=0.30`, `OUTPUT_PRICE_PER_MILLION=1.20` (peak, cache miss — worst-case оценка) со ссылкой на документацию.

### Presentation

`presentation/schemas.py`:

- `UsageResponse` — поля `UsageReport`;
- `ChatResponse` получает `usage: UsageResponse`;
- `ChatMessageResponse` получает опциональное `usage` (для перерисовки статистики после перезагрузки);
- `ChatDetailResponse` получает `dialog_usage` (накопленные токены, стоимость, остаток бюджета).

`presentation/routes.py`:

- `ContextLimitExceeded` → HTTP 413 с телом `{estimated_tokens, context_limit}`;
- остальная обработка ошибок без изменений.

### Frontend

- Панель статистики над чатом: прогресс-бар заполнения бюджета (зелёный, жёлтый ≥ 80%, красный при 100%), накопленные токены диалога, оценка стоимости `$`.
- Под каждым ответом ассистента мелкая строка: `запрос N · история M · ответ K`.
- Кнопка «Симулировать длинный диалог»: отправляет последовательно заготовленные длинные сообщения (~800–1200 токенов каждое) через обычный endpoint сообщений, после каждого ответа обновляет статистику, останавливается при HTTP 413.
- Баннер переполнения: «Диалог превысил лимит контекста (X из Y). Сообщение не отправлено и не сохранено. Начните новый чат».

## Демонстрация сценариев

Все сценарии выполняются в UI на живом API, результаты фиксируются в README `day8`:

1. **Короткий диалог** — 2–3 коротких сообщения; основная стоимость — токены ответов.
2. **Длинный диалог** — кнопка симуляции; видно, что `history_tokens` растёт линейно, а расход токенов за ход — быстрее линейного, потому что вся история пересылается каждым запросом.
3. **Переполнение** — продолжение симуляции: предупреждение ≥ 80%, затем HTTP 413; сообщение не отправлено и не сохранено, диалог нельзя продолжить без нового чата.

В README дополнительно документируются: реальный лимит контекста 1M токенов, вид настоящей ошибки API (`400`, `context_length_exceeded`), как изменить бюджет через `CONTEXT_LIMIT_TOKENS`.

## Ошибки и граничные случаи

- Оценка tiktoken может отличаться от точного `prompt_tokens` API — в UI и README локальные числа помечаются как оценка.
- Сообщение, превышающее бюджет само по себе, отклоняется с 413 так же, как и переполненная история.
- При отсутствии `usage` в ответе провайдера — `LLMGatewayError`, поведение как при любой ошибке провайдера.
- Старые `chats.json` без поля `usage` читаются корректно (`usage=None`), накопительные итоги начинают считаться с новых сообщений.

## Тестирование

- `TokenCounter`: пустой текст, известная строка, список сообщений.
- Agent: сплит запрос/история в `UsageReport`; переполнение — gateway не вызван, репозиторий не изменился; warning при ≥ 80%.
- Repository: `usage` сохраняется и восстанавливается; чтение старого файла без `usage`.
- API: 413 при переполнении с телом ошибки; `usage` в `ChatResponse`; `dialog_usage` в `ChatDetailResponse`.
- Gateway: парсинг `usage` из fake-клиента; маппинг `BadRequestError(context_length_exceeded)` в `ContextLimitExceeded`.
- Frontend: `npm run build`; ручной прогон трёх сценариев на живом API.

## Out of scope

- автообрезка или суммаризация истории при переполнении;
- точный токенизатор DeepSeek;
- учёт cache hit в стоимости (показываем worst-case);
- выбор модели в UI;
- изменения в `day6`/`day7`.
