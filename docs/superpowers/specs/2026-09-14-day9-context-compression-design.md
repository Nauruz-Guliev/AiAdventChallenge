# День 9: управление контекстом — сжатие истории (дизайн)

Дата: 2026-09-14. Основа: day8 (бюджет контекста + учёт токенов). Модель: `deepseek-flash` (реальный вывод провайдера при `DEEPSEEK_MODEL=deepseek-chat`), контекст 1M токенов, бюджеты приложения — наши.

## Постановка

День 8 замораживал чат при переполнении (413) и честно говорил: автообрезка — вне скоупа. День 9 реализует её как управляемое сжатие:

- последние N сообщений уходят «как есть»;
- остальное заменяется rolling-summary (одна свёртка на чат);
- summary хранится отдельно и подставляется в запрос вместо полной истории;
- в UI есть тумблер сжатия, чтобы сравнить качество ответов и расход токенов до/после.

## Ключевое решение: сжатие = сборка запроса, не удаление

Полная история сообщений в `chats.json` **никогда не удаляется**. В чате дополнительно храним `summary` (текст) и `summary_covers` (сколько первых сообщений свёртка покрывает). Тумблер `compress` в теле запроса решает, что пойдёт в API:

- `compress=false` — вся история как в day8 (включая 413 при переполнении);
- `compress=true` и оценка истории > `COMPRESS_AT_TOKENS` — запрос собирается из `[system: "Краткое содержание диалога: <summary>"] + KEEP_RECENT последних сообщений`.

Так сравнение до/после честно: один и тот же чат, один и тот же вопрос, разная сборка контекста.

## Конфигурация (env)

| Переменная | Дефолт | Смысл |
|---|---|---|
| `CONTEXT_LIMIT_TOKENS` | 8000 | жёсткий бюджет запроса (наследие day8) |
| `COMPRESS_AT_TOKENS` | 3000 | порог оценки истории, выше который сжатие нужно |
| `KEEP_RECENT_MESSAGES` | 10 | хвост диалога «как есть» |
| `SUMMARY_MAX_TOKENS` | 500 | целевая длина свёртки |

## Механика (backend)

1. `ChatRequest` получает поле `compress: bool = True`.
2. В `Agent.handle_message` при `compress=true`:
   - оценка токенов всей истории (`TiktokenCounter`, как в day8);
   - если `history_tokens <= COMPRESS_AT_TOKENS` — сжатие не нужно, запрос как обычно, в отчёте `applied=false`;
   - иначе — старая часть = история минус `KEEP_RECENT` последних сообщений. Если `summary` отсутствует или `summary_covers < len(старой части)` — вызываем суммаризатор:
     - промпт суммаризации: «Обнови краткое содержание диалога. Предыдущая свёртка: <summary или "нет">. Новые сообщения: <старая часть>. Сожми в ≤500 токенов: цели, факты, решения пользователя, открытые вопросы».
     - вызов через тот же `DeepSeekGateway` (те же цены, usage возвращаются);
     - новый summary и `summary_covers = len(старой части)` сохраняются в чат.
   - запрос = summary-system + хвост; повторная оценка; если всё равно > `CONTEXT_LIMIT_TOKENS` (хвост один гигантский) — `ContextLimitExceeded` (413, день 8 как страховка).
3. Ошибка суммаризации — `LLMGatewayError` (502 как сейчас), сообщения не сохраняются.
4. Успех: сохраняются user+assistant с usage; `summary`/`summary_covers` уже сохранены отдельным вызовом репозитория до отправки основного запроса (чтобы не потерять свёртку при падении основного вызова).

## Учёт (продолжение темы дня 8)

`UsageReport` дополняется вложенным `compression`:

```python
class CompressionReport(BaseModel):
    applied: bool          # сжатие было нужно и применено
    before_tokens: int     # оценка всей истории
    after_tokens: int      # оценка собранного контекста (summary + хвост)
    saved_tokens: int
    saved_percent: int
    summarization_tokens: int   # сколько стоила сама свёртка (0 если не обновлялась)
    summarization_cost_usd: float
```

`DialogUsage` без изменений (история в хранилище полная). `ChatSession` получает `summary: str | None = None`, `summary_covers: int = 0` — обратно совместимо со старыми чатами (default'ы).

## API

- `POST /api/v1/chats/{id}/messages` — тело `{"content": str, "compress": bool = True}`; ответ дополнен `usage.compression`.
- `GET /api/v1/chats/{id}` — `summary` в ответе чата, чтобы UI показывал «свёртка есть, покрывает M сообщений».
- 413/404/400 — без изменений.

## UI (day9)

- Тумблер «Сжатие истории» над composer; состояние в `localStorage`, шлётся в теле запроса; задизейблен во время загрузки.
- Чип под ответом ассистента при `compression.applied`: `было 5157 → стало 940 токенов (−82%) · свёртка −$0.00012`.
- В UsagePanel строка «Сжатие: off/standby/applied».
- Остальное (прогресс-бар бюджета, симуляция, markdown) — без изменений.

## Сравнение качества (ручками, по выбору пользователя)

Тест-ритуал в README:
1. Симуляцией надуть историю до порога; тумблер off → следующий вопрос упирается в 413 («так было в дне 8»);
2. тумблер on → тот же вопрос получает ответ; в чипе видно экономию;
3. вопросы на дальнюю память («что я просил в самом начале?», «назови деталь из 2-го сообщения») до/после включения сжатия на одном чате — фиксируем, что summary сохраняет, а что потеряно;
4. цифры `before/after` из чипа — сравнение расхода токенов.

## Тесты

Backend (TDD, фейковый gateway c детерминированным summary):
- пороги: ниже `COMPRESS_AT_TOKENS` — не суммаризируем; выше — суммаризируем ровно один раз при неизменной старой части (кэш summary по `summary_covers`);
- сборка: в запрос попадают summary-system + ровно `KEEP_RECENT` хвостовых сообщений в исходном порядке;
- 413 и при `compress=true`, если хвост сам сверх бюджета;
- сохранение `summary`/`summary_covers` через репозиторий; `usage.compression` в отчёте;
- матрица: тумблер off при большой истории = поведение day8 (полная история, возможный 413);
- репозиторий: round-trip summary-полей, legacy-чаты без полей;
- gateway: usage суммаризатор-вызова пробрасывается (покрытие существующими тестами).
Frontend: сборка vite + живой ритуал.

## Границы

- Одна rolling-свёртка на чат (не сегменты).
- Сжатие не удаляет историю; «очистить чат» остаётся ручным.
- Векторный поиск/иерархические свёртки — вне скоупа (упомянуть в README как «дале»).
- Скаффолд: копия day8 → day9 (переименование пакета/порт/заголовок), как day7→day8.
