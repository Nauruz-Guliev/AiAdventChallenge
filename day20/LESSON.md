# Day 20 — Конспект: оркестрация MCP

## 1. Композиция vs оркестрация

- **Композиция** (день 19) — цепочка инструментов **внутри** одного сервера.
- **Оркестрация** (день 20) — сервер сам ходит в **другие** MCP-серверы и координирует
  их. Оркестратор — одновременно MCP-сервер (для агента) и MCP-клиент (для соседей).

## 2. Оркестратор — это MCP-клиент

`client.py` открывает `mcp.Client(StdioServerParameters(...))` и вызывает инструмент
на удалённом сервере. `run_flow` держит **по одному клиенту на сервер** через
`AsyncExitStack` — не поднимает процесс на каждый шаг.

## 3. Выбор инструментов: `route`

`route()` строит список шагов `Step(server, tool, args)`:

- `weather` — только если указан город;
- `compose.search/summarize/save_to_file` — всегда;
- `scheduler.add_reminder` — только если просили напомнить;
- `notes.add_note` — всегда последним.

Условные шаги и есть **выбор инструментов** под запрос. `plan()` возвращает этот
список до выполнения.

## 4. `parse_goal`: rule-based маршрутизация

`parse_goal(goal)` извлекает параметры простыми правилами:

- город — regex `(?:в|во)\s+([А-ЯЁ][а-яё]+)`;
- напоминание — слово «напомн» в цели;
- тема — текст после «про»/«о»/«об».

Это учебный роутер, а не NLU. `route()` можно вызывать и с типизированными
параметрами — это надёжнее.

## 5. Передача данных между серверами

Шаги обмениваются данными через **контекст** `ctx`:

```
search.results ─► $search_text ─► summarize ─► $summary ─┐
                                                 │        └─► add_note(body)
                                                 └─► $markdown ─► save_to_file(content)
```

Аргумент-ссылка записывается как `$key` и резолвится из `ctx` перед вызовом. Так
выход одного сервера становится входом другого.

## 6. `trace` — доказательство порядка

Каждый шаг даёт запись:

```python
{"index": 0, "server": "weather", "tool": "get_weather",
 "args": {...}, "ok": True, "result": {...}}
```

`trace` после выполнения должен совпадать с `plan` до выполнения — это и есть проверка
«корректности выбора и порядка вызовов».

## 7. Обработка ошибок

Ошибка шага (например, недоступен wttr.in) записывается как `{ok: false, error}` и
**останавливает** флоу: в отчёте `ok=false`, но частичный `trace` сохраняется —
видно, где всё сломалось. Остальные серверы при этом не трогаются.

## 8. Как проверить

- `pytest -q` → 12 офлайн-тестов (роутер, trace, передача данных, заметки, stdio).
- stdio-тест реально поднимает `notes_server` как **отдельный** MCP-сервер и вызывает
  его через `client.call_tool` — это доказывает работу MCP-клиента офлайн.
- В opencode: длинный флоу одной фразой через `orchestrator_run_flow`.
