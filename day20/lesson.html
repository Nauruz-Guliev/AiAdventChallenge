01Композиция vs оркестрация

Композиция (день 19) — цепочка инструментов внутри одного сервера. Оркестрация (день 20) — сервер сам ходит в другие MCP-серверы и координирует их. Оркестратор одновременно MCP-сервер (для агента) и MCP-клиент (для соседей).

02Оркестратор — это MCP-клиент

client.py открывает mcp.Client(StdioServerParameters(...)) и вызывает инструмент на удалённом сервере. run_flow держит по одному клиенту на сервер через AsyncExitStack — не поднимает процесс на каждый шаг.

03Выбор инструментов: route

route() строит список шагов:

weather.get_weather — если указан город compose.search → summarize → save_to_file — всегда scheduler.add_reminder — если просили напомнить notes.add_note — всегда последним

Условные шаги и есть выбор инструментов под запрос. plan() возвращает этот список до выполнения.

04parse_goal: rule-based

Извлекаем параметры простыми правилами:

  • город — regex (?:в|во) +([А-ЯЁ][а-яё]+) (после «в» пробел);
  • напоминание — слово «напомн»;
  • тема — текст после «про»/«о»/«об».
Это учебный роутер, а не NLU. Для надёжности route() можно звать с типизированными параметрами.

05Передача данных между серверами

Шаги обмениваются данными через контекст: ссылка $key резолвится перед вызовом.

search.results → $search_text → summarize → $summary ─┬─► add_note(body)
                                                └─► $markdown → save_to_file

Так выход одного сервера становится входом другого.

06trace — доказательство порядка

{"index": 0, "server": "weather", "tool": "get_weather",
 "args": {...}, "ok": true, "result": {...}}

trace после выполнения должен совпадать с plan до выполнения — это проверка корректности выбора и порядка вызовов.

07Обработка ошибок

Ошибка шага (например, недоступен wttr.in) записывается как {ok: false, error} и останавливает флоу: в отчёте ok=false, но частичный trace сохраняется — видно, где сломалось. Остальные серверы не трогаются.
