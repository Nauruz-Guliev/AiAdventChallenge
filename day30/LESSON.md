# День 30 — Конспект: локальная LLM как приватный сервис

## 1. Зачем шлюз, если уже есть Ollama

Ollama — отличный **рантайм модели**: загрузка весов, `num_ctx`, стриминг, `/api/chat`. Но он не
предназначен быть публичным сервисом:

- нет авторизации — кто дотянулся до порта, тот и пользуется моделью;
- нет ограничения частоты — один клиент займёт GPU целиком;
- нет лимита на размер запроса — длинный промпт выбьет контекст или память;
- нет очереди и понятного поведения под нагрузкой.

Поэтому мы **не открываем Ollama в сеть**, а ставим перед ним тонкий шлюз. Шлюз знает про
Ollama только HTTP (порт `11434` на `localhost`) и добавляет сервисные вещи. Это классическое
разделение: рантайм модели ≠ сервис доступа.

```
клиент → шлюз (авторизация, лимиты, очередь, метрики) → Ollama (генерация)
```

## 2. OpenAI-совместимость как контракт

Мы отдаём `POST /v1/chat/completions` в формате OpenAI. Это не самоцель: совместимый контракт
означает, что сервис заработает с любым готовым клиентом (SDK `openai`, чат-UI, LangChain) —
достаточно поменять `base_url`. Меняем шину, не изобретаем свой протокол.

Маппинг «наш JSON → Ollama»:

| OpenAI | Ollama `/api/chat` |
|---|---|
| `messages` | `messages` |
| `max_tokens` | `options.num_predict` |
| `temperature` | `options.temperature` |
| `stream` | `stream` |
| `usage.prompt_tokens` | `prompt_eval_count` |
| `usage.completion_tokens` | `eval_count` |

Ошибки тоже в формате OpenAI: `{"error": {"message", "type", "code"}}` — клиенты умеют их
разбирать единообразно.

## 3. Token bucket: как считается rate limit

Идея: у каждого клиента есть «ведро» токенов ёмкостью `burst`. Каждый запрос стоит 1 токен.
Ведро непрерывно пополняется со скоростью `per_minute / 60` в секунду. Пустое ведро → `429`.

```python
tokens = min(capacity, tokens + elapsed * refill_per_sec)
if tokens >= cost: tokens -= cost
else: retry_after = (cost - tokens) / refill_per_sec
```

Почему не «N запросов в фиксированную минуту»? Token bucket сглаживает: короткий всплеск
(`burst`) разрешён, а длинный поток ограничен средней скоростью. Мы делим ведро **на ключ**
(иначе — на IP): два клиента не мешают друг другу. `Retry-After` подсказывает, когда повторить.

## 4. Лимит контекста: почему эвристика, а не точный токенайзер

Точный подсчёт токенов требует токенайзера конкретной модели. Для шлюза этого мало нужно:
достаточно **грубой** оценки, чтобы отсечь заведомо слишком большие промпты. Оценка
`~4 символа на токен` + 4 токена на каждое сообщение. Проверка простая:

```
оценка_промпта + max_tokens <= num_ctx
```

Иначе — `400 context_length_exceeded` с подсказкой. Мы **до** вызова Ollama понимаем, что
запрос не влезет, и не тратим GPU. Сообщение об ошибке при этом человеческое, а не «Ollama
вернул 500».

## 5. Конкурентность: почему `MAX_CONCURRENCY=1`

Ollama при `OLLAMA_NUM_PARALLEL=1` (по умолчанию для одной модели) обрабатывает запросы по
одному. Значит, толпа одновременных запросов не ускорит работу — только выстроит очередь.
Мы честно ограничиваем одновременную работу семафором (`1`) и разрешаем небольшую очередь
(`8`). Кто не влез в очередь — получает `503` сразу, а не висит минуту.

Для стриминга важно: слот занимается **до** старта ответа (иначе перегрузку не отдать как
`503`), а освобождается в `finally` генератора — даже если клиент отвалился.

## 6. Что показал нагрузочный тест

24 одновременных запроса на слабой домашней машине дали: 46% `200`, 50% `429` (сработал rate
limit), 4% `503` (переполнение очереди), p50 ≈ 3.2 с, p95 ≈ 4.5 с. Ключевое — **сервис остался
жив** и очередь опустела. Это и есть «стабильность»: управляемая деградация вместо падения.
p95 показывает «хвост» — отдельные медленные запросы, которые среднее прячет.

## 7. Приватность

Вся цепочка работает дома: браузер → шлюз на этом же ПК → Ollama на `localhost`. Данные не
уходят в облако. Ключ защищает доступ внутри домашней сети. Для «настоящего» приватного
сервиса поднимают то же самое на VPS/домашнем сервере, но там нужен ещё TLS.

## 8. Как прикрутить TLS (за рамками дня)

Шлюз отдаёт обычный HTTP. Проще всего поставить перед ним **Caddy** как reverse proxy — он сам
получает сертификат Let's Encrypt:

```
llm.example.com {
    reverse_proxy localhost:8000
}
```

Тогда клиенты ходят на `https://llm.example.com`, а наш шлюз остаётся внутренним. Ключ и лимиты
продолжают работать. Альтернатива — `uvicorn --ssl-keyfile/--ssl-certfile` с самоподписанным
сертификатом для локальной сети.

## 9. Главные выводы

1. Локальную модель выставляют в сеть **через шлюз**, а не напрямую.
2. OpenAI-совместимый контракт → бесплатная совместимость с готовыми клиентами.
3. Базовые ограничения — это не «фича на потом», а условие стабильности: авторизация, rate
   limit, лимит контекста, очередь.
4. Перегрузку нужно уметь **отдавать кодом** (`429`/`503` + `Retry-After`), а не падать.
5. Метрики (`p50/p95`, счётчики) делают поведение сервиса наблюдаемым.
