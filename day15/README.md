# День 15: контролируемые переходы состояний

Самостоятельное продолжение `day14`. Поверх агента с инвариантами, памятью и
конечным автоматом задачи добавлен **явный контроль переходов**: у задачи есть
объявленные состояния и таблица разрешённых переходов, а ассистент не может
перепрыгнуть этап.

`day6`–`day14` не изменяются.

## Что изучаем

В дне 14 автомат уже был, но переходы «зашивались» в методы, план принимался
автоматически, а недопустимый переход молча игнорировался. День 15 делает
жизненный цикл задачи явным и проверяемым.

| состояние | смысл |
| --- | --- |
| `planning` | ассистент предлагает план |
| `approval` | план ждёт утверждения пользователем |
| `execution` | ассистент выполняет шаги плана |
| `validation` | ассистент проверяет результат |
| `done` | задача завершена |

Разрешённые переходы:

```
planning → approval → execution → validation → done
execution → execution (следующий шаг)
```

## Как это устроено

1. В `app/domain/task_state.py` переходы описаны **таблицей** `ALLOWED_TRANSITIONS`
   и событиями (`propose_plan`, `approve_plan`, `complete_step`,
   `complete_validation`). Сменить стадию можно только через `transition()`.
2. Ассистент **сам просит переход** структурированным ответом
   (`{"event": "complete_step", "result": "..."}`). Если JSON нет — работает
   текстовый фолбэк на ожидаемое событие этапа.
3. Недопустимое событие (например `{"event": "complete_validation"}` на этапе
   `execution`) отклоняется: состояние **не меняется**, попытка попадает в журнал
   (последние 5), ответ аннотируется «⚠ …».
4. Реализацию нельзя начать до `approve_plan`, а финал — до
   `complete_validation`. Гейт утверждения: на стадии `approval` модель не
   вызывается, эндпоинт сообщений отдаёт уведомление.
5. Пауза — отдельный флаг; `resume` не меняет стадию и сохраняет журнал
   отклонённых переходов. На `approval` пауза и продолжение остаются на
   `approval`.

## Что проверено

- **Прыжок из `execution` в `done`:** модель просит `complete_validation` на
  этапе выполнения → 409/аннотация, состояние не двигается.
- **Реализация до утверждения:** на `approval` сообщение возвращает
  «План ждёт утверждения», модель не вызывается; старт только по
  `approve_plan`.
- **Финал без проверки:** `complete_validation` вне этапа `validation`
  отклоняется.
- **Продолжение после паузы:** пауза/продолжение на `approval` сохраняет стадию,
  выполнение продолжается с того же шага.
- **Таблица переходов** отдаётся в `GET /api/task/transitions` и показывается в
  панели задачи.

```powershell
python -m venv .venv

# .env: DEEPSEEK_API_KEY=... (см. .env.example)
```

```powershell
cd day15\frontend

```

Если `day14` держит порт 8000/5173 — сначала остановите его.

## API

- `GET /api/task/transitions` — таблица состояний, событий и разрешённых
  переходов;
- `POST /api/task/transition {event}` — единственная точка смены стадии;
  недопустимое событие → 409 с причиной и записью в журнал; при паузе → 409;
- `POST /api/chats/{id}/messages` на стадии `approval` возвращает уведомление без
  вызова модели;
- состояние задачи отдаёт `allowed_stages` и `rejections`;
- остальные эндпоинты — как в `day14`.

## Честные ограничения

- Ассистент просит переход строгим JSON; при несоблюдении формата работает
  текстовый фолбэк (считается ожидаемое для этапа событие).
- Журнал отклонённых переходов ограничен последними пятью записями.
- Переходы инициирует бэкенд по запросу ассистента; прямых «прыжков» вперёд нет
  по построению таблицы.

## Структура

- `app/domain/task_state.py` — состояния, события, таблица переходов, журнал
  отклонений;
- `app/application/task_engine.py` — промпты этапов, разбор запроса перехода,
  аннотация отказа;
- `app/application/agent.py` — вызов модели, применение перехода, аннотация;
- `app/presentation/routes.py` — `GET /api/task/transitions`,
  `POST /api/task/transition`, гейт утверждения;
- `frontend/src/components/TaskStatePanel.jsx` — стадии, кнопка «Утвердить план»,
  доступные переходы и журнал отклонений.
