Планировщик и фоновые задачи

День 17 — инструмент, который отвечает на запрос. Здесь — инструмент, который работает во времени: помнит задачи, тикает и копит данные, даже когда opencode закрыт, а при обращении отдаёт агрегированную сводку.

Python · mcp v2 · stdio · SQLite · отдельный демон · day17 weather

1.Задание дня

Сделать MCP-инструмент с отложенным или периодическим выполнением. Инструмент должен:

  • 👉 сохранять данные (JSON / SQLite);
  • 👉 выполняться по расписанию;
  • 👉 возвращать агрегированный результат.

Примеры из задания: напоминание, периодический сбор данных, регулярный summary. Результат — «агент, который работает 24/7 и периодически выдаёт сводку».

2.Почему MCP — pull, а не push

Ключевой факт: MCP-сервер не может сам отправить агенту сообщение «эй, вот сводка». Агент сам решает, когда вызвать инструмент. Значит «периодически выдаёт» раскладывается на две части:

Демон (по расписанию)

материализует сводки в SQLite

+

Агент (когда спросит)

читает их инструментом

Следствие для дизайна

Кто-то должен работать, даже когда opencode закрыт. Поэтому планировщик — это отдельный процесс-демон, а не код внутри MCP-сервера (сервер живёт ровно столько, сколько открыт opencode).

3.Архитектура: два процесса и одна SQLite

Как устроено

opencode ──stdio──► server.py ─┐
                                ├─► day18/state.db (SQLite, WAL)
worker.py (демон, тик 1 c) ─────┘
   └──► sources.sample_weather() ──► day17/weather_api.py ──► wttr.in
ПроцессРольЖивёт
server.pyMCP: принимает задачи, отдаёт агрегатыпока открыт opencode
worker.pyдемон: выполняет задачи по расписанию24/7, отдельно
state.dbобщее состояние: задачи, замеры, сводкина диске

Общей памяти между процессами нет — только БД. Поэтому каждый можно перезапускать независимо, а состояние не теряется.

Оба процесса должны смотреть в одну БД

Путь по умолчанию — day18/state.db, считается от файла scheduler.py, а не от текущей папки, чтобы запуск из разных мест не создавал разные БД. Переопределяется переменной SCHEDULER_DB.

4.Ядро: задачи, сроки, агрегация

Вся логика и SQL — в scheduler.py, чистыми функциями над соединением. Их используют демон, сервер и тесты — поэтому проверять можно без процессов.

•Три таблицы

tasks(id, kind, city, interval_seconds, next_run_at, payload,
      active, fired_at, acknowledged, created_at)
samples(id, task_id, city, temperature_c, weather, taken_at)
summaries(id, task_id, city, period_seconds, window_start, window_end,
          n, avg_c, min_c, max_c, created_at)

kind — reminder (разовый, интервала нет), collect (сбор), summary (сводка). Время — epoch-секунды (int, UTC).

•Кто «созрел»

def due_tasks(conn, at):
    return conn.execute(
        "SELECT * FROM tasks WHERE active = 1 AND next_run_at <= ? "
        "ORDER BY next_run_at, id", (at,)).fetchall()

•Перенос без «догона»

def reschedule(conn, task, at):
    conn.execute("UPDATE tasks SET next_run_at = ? WHERE id = ?",
                 (at + task["interval_seconds"], task["id"]))
Почему это важно

Если демон был выключен час, задача выполнится один раз, а не залпом за весь простой. Новый срок считается от момента выполнения (at + interval), поэтому расписание не «разъезжается».

•Агрегация

SELECT COUNT(*) AS n, AVG(temperature_c) AS avg_c,
       MIN(temperature_c) AS min_c, MAX(temperature_c) AS max_c
FROM samples WHERE city = ? AND taken_at >= ? AND taken_at <= ?

Пустое окно → count=0, значения None — не падаем на отсутствии данных.

5.Демон: тик и выполнение

Раз в секунду демон выбирает созревшие задачи и выполняет каждую по типу.

day18/worker.py

def tick(conn) -> int:
    due = scheduler.due_tasks(conn, scheduler.now())
    for task in due:
        try:
            execute_task(conn, task)
        except Exception as exc:   # одна задача не роняет демон
            print(f"[worker] ошибка задачи #{task['id']}: {exc}", file=sys.stderr)
    return len(due)
  • collect → замер → samples → перенос;
  • summary → агрегат за окно → summaries → перенос;
  • reminder → fired_at=now, active=0.
Устойчивость

Если источник недоступен (SourceError), замер пропускается, но срок всё равно переносится — расписание не теряется. Ошибка логируется, демон продолжает работать.

6.Источник данных

Домен сбора отделён от планировщика: демон не знает, откуда данные. Он зовёт sources.sample_weather(city), а внутри — переиспользование дня 17.

day18/sources.py

def sample_weather(city: str) -> dict:
    import weather_api            # day17, добавлен в sys.path
    try:
        place = weather_api.geocode(city)
        current = weather_api.current_weather(place.latitude, place.longitude)
    except weather_api.WeatherError as exc:
        raise SourceError(str(exc)) from exc
    return {"temperature_c": current["temperature_c"],
            "weather": current["weather"]}

В тестах источник подменяется фейком — сеть не нужна, планировщик проверяется изолированно.

Сервер не выполняет задачи — только пишет их в БД и читает агрегаты. Выполняет демон. Так интерфейс и исполнитель разделены.
