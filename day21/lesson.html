01Что и зачем: RAG и индекс

LLM знает только то, что попало в контекст. RAG (Retrieval-Augmented Generation) дополняет ответ релевантными фрагментами из базы знаний. Чтобы их находить быстро, документы заранее:

1. chunking — режем на смысловые единицы 2. embeddings — каждый чанк → вектор 3. index — «вектор + метаданные» каждого чанка

На запрос эмбеддим его тем же способом, ищем ближайшие чанки по cosine similarity и подставляем их текст в промпт.

02Архитектура пайплайна

corpus/*.md
   │  load            (source, title, text)
   ▼
chunking ──┬── fixed-size   (~120 токенов, overlap 20)
           └── structure    (по заголовкам # → ## → ###)
   │  чанки + метаданные
   ▼
embeddings        (sentence-transformers, батчами, L2-normalize)
   │  вектор на чанк
   ▼
index (JSON: chunk_id, source, title, section, strategy, text, embedding, …)
   │
   ├─► compare.py   сравнение стратегий (метрики + качество извлечения)
   └─► query.py     семантический поиск top-k (RAG-выборка)

Ключевой приём: один корпус прогоняем через обе стратегии независимо — сравнение честное, на одних данных.

03Шаг 1. Корпус KMP

Тема — Kotlin Multiplatform. Собираем максимум актуальной информации скриптом fetch_docs.py прямо из официальных источников на GitHub:

144 документа, ≈1.8 млн символов (≈1000 страниц). Корпус фиксируется в репозитории как markdown, поэтому индексация воспроизводима.

Почему raw GitHub, а не HTML. kotlinlang.org — SPA, обычный HTTP-запрос отдаёт пустую страницу. Исходники документации лежат в репозитории как markdown — их и берём напрямую. Из Writeside-текста удаляем служебные теги (strip_writeside), а заголовок достаём из [//]: # (title: …).

04Шаг 2. Chunking — две стратегии

Чанк — компромисс: крупный размывает смысл, мелкий теряет контекст. Поэтому делаем две стратегии и сравниваем.

A. Фиксированный размер — chunk_fixed

Окна по chunk_size токенов со сдвигом step = chunk_size − overlap. Перекрытие сохраняет контекст на стыках.

def chunk_fixed(text, chunk_size=120, overlap=20, source="", title="", tokenizer=None):
    spans = _spans(text, tokenizer)           # границы токенов (модель) или слов
    step = max(1, chunk_size - overlap)       # 120 - 20 = 100
    i = idx = 0
    while i < len(spans):
        j = min(i + chunk_size, len(spans))
        yield Chunk(chunk_id=f"{source}:fixed:{idx}",
                    section="fixed", strategy="fixed",
                    text=text[spans[i][0]:spans[j-1][1]],
                    char_offset=spans[i][0], token_count=j - i)
        if j == len(spans): break
        i += step; idx += 1

Плюс: ровные чанки, предсказуемая стоимость. Минус: граница проходит по слову, игнорируя структуру.

B. По структуре — chunk_structure

Режем по заголовкам markdown (^#{1,6}\s), отслеживая путь # A > ## B > ### C. Мелкие секции склеиваем до min_tokens.

def chunk_structure(markdown, max_tokens=120, min_tokens=48, source="", title=""):
    sections = _split_sections(markdown, title, source)   # (path, text, offset)
    units = []                                   # длинные секции режем на окна
    for path, text, off in sections:
        if count_tokens(text) <= max_tokens:
            units.append((path, text, off))
        else:
            units += [(path, w, off + o) for w, o, _ in
                      _slice_windows(text, max_tokens, overlap=0)]
    # склеиваем мелкие unit'ы до min_tokens, не превышая max_tokens

Плюс: чанк — законченная секция, section даёт точную навигацию. Минус: размеры плавают, нужна склейка.

Лимит модели: max_seq_length=128. Всё, что длиннее, обрезается при эмбеддинге. Поэтому окно и max_tokens держим ≤120. А токенизатор модели даёт offset mapping — границы токенов в символах, по которым режем исходный текст точно по токенам (а не по словам).

05Шаг 3. Эмбеддинги

Эмбеддер — текст → вектор: похожие по смыслу тексты дают близкие векторы. Контракт:

class Embedder:
    dim: int
    def embed(self, texts) -> np.ndarray: ...   # (N, D)

Две реализации:

  • SentenceTransformerEmbedder — модель paraphrase-multilingual-MiniLM-L12-v2 (RU+EN), батчами, normalize_embeddings=True;
  • FakeEmbedder — детерминированный хэш текста → вектор. Нужен для офлайн-тестов и прогонов без скачивания модели (семантики не даёт).
Зачем FakeEmbedder. Логику chunking и индекса тестируем без torch (~2 ГБ) и модели (~470 МБ). Настоящая модель грузится только на финальном прогоне. Разделение зависимостей = быстрые офлайн-тесты.

06Шаг 4. IndexStore — хранение и поиск

Индекс — это матрица векторов (N, D) + список метаданных. Строим, сохраняем в JSON, грузим, ищем косинусом:

class IndexStore:
    @classmethod
    def build(cls, chunks, embedder, model_name):   # embed + L2-normalize
    def save(self, path):                            # JSON: meta + chunks + embedding
    @classmethod
    def load(cls, path):
    def search(self, query_vec, top_k=5):
        q = query_vec / norm(query_vec)
        scores = self.embeddings @ q                 # cosine (векторы нормированы)
        order = np.argsort(-scores)[:top_k]
        return [Hit(...) for i in order]

Нормированные векторы + скалярное произведение = косинус за одну операцию.

Формат файла index/structure.json

{
  "meta": { "strategy": "structure", "model": "paraphrase-multilingual-MiniLM-L12-v2",
            "embedding_dim": 384, "num_chunks": 4817, "created_at": "..." },
  "chunks": [
    { "chunk_id": "kmp-docs/071-…-expect-actual.md:struct:2",
      "source":   "kmp-docs/071-development-multiplatform-expect-actual.md",
      "title": "Expected and actual declarations",
      "section": "Rules for expected and actual declarations",
      "strategy": "structure", "char_offset": 812, "token_count": 101,
      "text": "…", "embedding": [0.011, -0.023, …] }
  ]
}
Альтернативы. Формат JSON портируем и читаем. Для больших объёмов — SQLite (метаданные + blob-векторы) или FAISS (быстрый ANN-поиск). Здесь ~5000 чанков, честный перебор numpy быстрее и проще.

ПолеСмысл

titleзаголовок документа
sectionпуть заголовков или "fixed"
chunk_id{source}:{strategy}:{i}, уникален

char_offsetпозиция начала чанка в документе

Именно метаданные превращают «нашёлся вектор» в «нашёлся фрагмент вот из этого документа, вот из этой секции».

11Подводные камни и выводы

  • Тяжёлые зависимости. sentence-transformers тянет torch (~2 ГБ) + модель ~470 МБ → отсюда FakeEmbedder для тестов.
  • Мусор в чанках. Writeside-теги и навигацию из HTML надо чистить, иначе эмбеддинги шумятся.
  • min_tokens и overlap сильно влияют на результат: большой min склеит секции, малый наплодит огрызков.
  • JSON-индекс крупный (векторы как float). Для продакшна — бинарный формат / FAISS.

Итог: локальный индекс KMP-документов с эмбеддингами и метаданными, две стратегии chunking с честным сравнением и семантический поиск для RAG.
