# Day 21 — Конспект: индексация документов для RAG

## 1. Зачем индекс

LLM знает только то, что влезло в контекст. RAG (Retrieval-Augmented Generation)
дополняет ответ **релевантными фрагментами** из базы знаний. Чтобы их найти, документы
заранее:

1. режутся на **чанки** (chunking) — мелкие смысловые единицы;
2. превращаются в **эмбеддинги** — векторы фиксированной длины;
3. складываются в **индекс** — «вектор + метаданные» каждого чанка.

На запрос мы эмбеддим его тем же способом и ищем ближайшие чанки (cosine similarity),
а их тексты подставляем в промпт.

## 2. Chunking

Чанк — компромисс. Слишком крупный: размывает смысл, не влезает в контекст. Слишком
мелкий: теряет контекст, плохо эмбеддится. Две стратегии:

### 2.1 Фиксированный размер (`chunk_fixed`)

Режем поток на окна по `chunk_size` токенов со сдвигом `step = chunk_size - overlap`.
`overlap` сохраняет контекст на стыках (предложение не «разрывается» без следа).

```python
chunk_fixed(text, chunk_size=120, overlap=20)   # step = 100
```

- Плюс: ровные чанки, предсказуемая стоимость.
- Минус: граница проходит по слову/предложению, игнорируя структуру.

### 2.2 По структуре (`chunk_structure`)

Режем по заголовкам markdown (`^#{1,6}\s`), отслеживая путь (`# A > ## B > ### C`).
Мелкие секции склеиваются с соседними до `min_tokens`, чтобы не плодить огрызки.

```python
chunk_structure(markdown, max_tokens=120, min_tokens=48)
```

- Плюс: чанк = законченная секция; `section` даёт точную навигацию.
- Минус: размеры плавают (от абзаца до простыни), нужна склейка мелких.

## 3. Токены и перекрытие

Размер удобно мерить в **токенах**, а не символах: у модели ограничение контекста — в
токенах. `count_tokens` использует токенизатор модели, а без него — приблизительно по
словам. `overlap` — доля перекрытия соседних окон.

**Важно:** у модели есть `max_seq_length` (у нашей MiniLM — 128). Всё, что длиннее,
обрезается при эмбеддинге. Поэтому и размер окна, и `max_tokens` секций держим ≤ 120 —
иначе часть текста молча теряется. Токенизатор модели даёт не только количество токенов,
но и **offset mapping** (границы токенов в символах) — по ним мы режем исходный текст
точно по токенам.

## 4. Эмбеддинги

Эмбеддер превращает текст в вектор: похожие по смыслу тексты → близкие векторы. Мы
берём `paraphrase-multilingual-MiniLM-L12-v2` (мультиязычный: RU+EN), L2-нормализуем
векторы и считаем косинус.

```python
class Embedder:            # контракт
    dim: int
    def embed(self, texts): ...
```

- `SentenceTransformerEmbedder` — настоящая модель (батчами, `normalize_embeddings=True`).
- `FakeEmbedder` — детерминированный хэш → вектор. Нужен для офлайн-тестов и для
  прогона пайплайна без скачивания модели (семантики не даёт).

Разделение важно: **логику** индекса и chunking’а тестируем на `FakeEmbedder`, а
настоящую модель грузим только на финальном прогоне.

## 5. Cosine-поиск

При одинаковой длине и норме `1` косинус = скалярное произведение. Весь поиск —
одна операция `embeddings @ query` и `argsort`:

```python
scores = self.embeddings @ q     # (N, D) @ (D,) -> (N,)
order = np.argsort(-scores)[:top_k]
```

Поэтому индекс хранится как матрица `(N, D)`, а не как список списков.

## 6. Метаданные

Вектор без метаданных бесполезен: нашёл чанк — нужно знать **откуда** он. Поэтому в
индекс пишем `source`, `title`, `section`, `chunk_id`, `strategy`, `char_offset`,
`token_count`. Из них собирается ссылка/цитата в ответе RAG.

## 7. Хранение индекса

Формат — JSON: `{meta, chunks:[{…, embedding:[…]}]}`. Плюсы: портируемо, читаемо,
без нативных зависимостей. Для больших объёмов альтернативы: **SQLite** (метаданные +
blob-векторы) и **FAISS** (быстрый ANN-поиск). Здесь объём (~1000 чанков) позволяет
честный перебор numpy.

## 8. Сравнение стратегий

`compare.py` считает метрики и качество извлечения:

- структурные: `num_chunks`, `avg/min/max/std_tokens`, `total_tokens`;
- прикладные: `hit_rate` — доля запросов, где ожидаемый документ попал в top-k.

Вывод из прогона: `fixed` даёт ровные чанки (std меньше) и меньше накладных, `structure`
даёт больше чанков, но каждый — законченная секция с осмысленным `section`, что лучше
для точных/навигационных запросов.

## 9. Как воспроизвести с нуля

Все команды — в PowerShell **из папки `day21`**. Скрипты запускаем только через
интерпретатор venv: `& ".venv\Scripts\python.exe" <скрипт>`. Просто `query.py "..."`
PowerShell не выполнит — это файл, а не команда.

```powershell
cd day21
$env:PYTHONIOENCODING="utf-8"; [Console]::OutputEncoding=[System.Text.Encoding]::UTF8

python -m venv .venv
& ".venv\Scripts\python.exe" -m pip install -r requirements.txt

# 1) (опционально) заново собрать корпус KMP из GitHub raw
& ".venv\Scripts\python.exe" fetch_docs.py

# 2) офлайн-прогон пайплайна (без модели)
& ".venv\Scripts\python.exe" pipeline.py --strategy both --embedder fake

# 3) реальные эмбеддинги
& ".venv\Scripts\python.exe" pipeline.py --strategy both --embedder sentence

# 4) сравнение и поиск
& ".venv\Scripts\python.exe" compare.py --embedder sentence
& ".venv\Scripts\python.exe" query.py "how do expect and actual declarations work" --top 3

# 5) тесты
& ".venv\Scripts\python.exe" -m pytest -q
```

## 10. Подводные камни

- **Тяжёлые зависимости.** `sentence-transformers` тянет `torch` (~2 ГБ), модель ~470 МБ.
  Поэтому пайплайн умеет работать на `FakeEmbedder`.
- **Кодировка.** Кириллица в PowerShell: `$env:PYTHONIOENCODING="utf-8"`.
- **Мусор в чанках.** Writeside-теги и навигацию из HTML корпуса надо чистить
  (см. `strip_writeside` в `fetch_docs.py`), иначе эмбеддинги «зашумляются».
- **`min_tokens` влияет на всё.** Слишком большой — секции склеятся в кашу; слишком
  малый — много огрызков.
- **JSON-индекс крупный.** Векторы как список float занимают десятки МБ; для продакшна
  — бинарный формат (`.npy`/FAISS).
