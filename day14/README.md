# День 14: инварианты и ограничения состояния

Самостоятельное продолжение `day13`. Поверх агента с профилем, памятью и
конечным автоматом задачи добавлены **инварианты** — ограничения, которые
ассистент не имеет права нарушать: выбранная архитектура, принятые технические
решения, ограничения по стеку и бизнес-правила.

`day6`–`day13` не изменяются.

## Что изучаем

Агент может дать формально правильный, но неприемлемый для проекта ответ
(«перепиши на другом языке», «добавь зависимость»). День 14 вводит явные
инварианты: они лежат отдельно от диалога, подставляются в каждый запрос и
проверяются до того, как модель начнёт отвечать.

| категория | смысл | пример |
| --- | --- | --- |
| `architecture` | выбранная архитектура | переходы автомата ведёт бэкенд |
| `decision` | принятые технические решения | все вызовы LLM — через один шлюз |
| `stack` | ограничения по стеку | только Python и React, без новых зависимостей |
| `business` | бизнес-правила | данные хранятся только локально |

## Как это устроено

1. Инварианты лежат в `data/invariants.json` — **отдельно от чатов и состояния
   задачи**. При первом запуске файл засеивается реальными инвариантами проекта.
2. Перед основным ответом запускается **LLM-страж**: он получает список
   инвариантов и сообщение пользователя и возвращает строгий JSON
   `{"violates": bool, "invariant_id": ..., "reason": ...}`.
3. Если нарушения нет — инварианты добавляются в system prompt, и агент отвечает
   как обычно (модель явно учитывает их в рассуждениях).
4. Если нарушение есть — основная модель **не вызывается**. Бэкенд отдаёт
   детерминированный отказ: какой инвариант нарушен и почему. Этап и шаг задачи
   при этом **не меняются** (как на паузе).
5. Сомнительные запросы страж трактует как «не нарушение»; если страж упал или
   вернул невалидный JSON — срабатывает fail-open, ответ идёт обычным путём.

## Что проверено

- **Конфликт запроса и инварианта:** «сделай на Node.js» → отказ, контент-модель
  не вызвана, автомат задачи не сдвинулся.
- **Объяснение отказа:** текст называет инвариант, его категорию и причину;
  в UI пузырь подсвечен и подписан «запрос отклонён».
- **Отсутствие конфликта:** обычный запрос проходит с блоком инвариантов в
  промпте.
- **Пустой список инвариантов:** страж не вызывается вовсе.
- **Сбой стража:** fail-open, ответ штатный.

## Запуск

```powershell
# backend (Windows)
cd day14\backend
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
# .env: DEEPSEEK_API_KEY=... (см. .env.example)
.venv\Scripts\python -m uvicorn app.main:app --reload
```

```powershell
# frontend — во втором терминале
cd day14\frontend
npm install
npm run dev   # http://localhost:5173
```

Если `day13` держит порт 8000/5173 — сначала остановите его.

## API

- `GET /api/invariants` · `POST /api/invariants` · `DELETE /api/invariants/{id}` —
  список, добавление и удаление инвариантов;
- `POST /api/chats/{id}/messages` возвращает поле `violation` с нарушенным
  инвариантом и причиной;
- эндпоинты состояния задачи и остальные — как в `day13`.

## Честные ограничения

- Проверка — один дополнительный запрос к модели на каждое сообщение.
- Страж может ошибаться на неоднозначных формулировках (смягчено правилом
  «сомнительное — не нарушение»); при сбое стража — fail-open.
- Отказ не сохраняет структурированную пометку в истории чата: после перезагрузки
  виден только текст отказа.

## Структура

- `app/domain/invariant.py` — `Invariant`, категории и подписи;
- `app/application/invariant_guard.py` — промпт стража, разбор ответа, шаблон отказа;
- `app/application/ports/invariant_repository.py` · `app/infrastructure/json_invariant_repository.py` — хранилище `data/invariants.json`;
- `app/application/agent.py` — вызов стража до основного ответа, блок инвариантов в промпте;
- `app/presentation/routes.py` — CRUD инвариантов и поле `violation` в ответе;
- `frontend/src/components/InvariantsPanel.jsx` — список, добавление и удаление инвариантов.
