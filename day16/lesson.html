День 16 · Model Context Protocol

MCP: подробный урок

Как устроен Model Context Protocol, почему он появился, как работает наш пример (сервер + клиент по stdio) и как настроить MCP самому — от нуля до конфига в реальном приложении.

Проект: AI Advent Challenge · пример: day16/ · SDK: MCP Python v2

1Зачем нужен MCP

Проблема, которую решает протокол.

У тебя есть LLM-приложение: чат, IDE, агент. Ты хочешь дать ему доступ к разным вещам — файлам, базе данных, Jira, календарю, поиску. Казалось бы, что сложного: просто напиши код, который это умеет.

Сложность появляется, когда таких интеграций много, а приложений — тоже много. Без общего стандарта каждая пара «приложение × сервис» — это свой самодельный протокол: свой формат «вот список моих функций», свой формат вызова, своя обработка ошибок. Получается N интеграций × M приложений комбинаций, и каждую надо поддерживать.

Идея MCP

Один общий протокол. Сервер один раз описывает свои возможности по стандарту — и любое клиентское приложение, понимающее протокол, может ими пользоваться. Число интеграций падает с N×M до N+M.

Аналогия — USB-C: раньше у каждого устройства был свой разъём, теперь есть общий стандарт, и любое устройство совместимо с любым компьютером. MCP — это «USB-C для инструментов LLM».

Что важно понять: MCP — это не «плагин для ChatGPT» и не магия. Это протокол обмена сообщениями (как HTTP для сайтов), поверх которого сервер отдаёт инструменты, а клиент их вызывает.

2Три роли: host, client, server

Разделяй эти слова — дальше они встречаются постоянно.

host

LLM-приложение целиком: чат, IDE, агент. То, с чем говорит пользователь.

→

client

Часть host, которая говорит по MCP. На каждый сервер — свой клиент внутри host.

↔

server

То, что пишешь ты. Отдаёт инструменты и данные. С моделью напрямую не общается.

В нашем примере роль host играет client.py (минимальное приложение), а server — server.py. В реальной жизни host — это Claude Desktop, Cursor, VS Code и т.п.

Ключевая мысль

Сервер никогда не вызывает модель. Он просто умеет выполнять инструменты. Решение «какой инструмент вызвать» принимает модель внутри host, а host через client отправляет серверу запрос.

3Три примитива сервера

Сервер может отдавать ровно три вида вещей. Отличие — кто решает их использовать.

ПримитивКто управляетЧто этоHTTP-аналогия
Toolsмодельфункция, которую модель вызывает для действияPOST
Resourcesприложениеданные, которые host кладёт модели в контекстGET
Promptsпользовательпереиспользуемый шаблон сообщенийсохранённый запрос

Смысл разделения — в колонке «кто управляет»:

  • Tool запускается, потому что так решила модель.
  • Resource подключается, потому что так решило приложение («модели нужно содержимое этого файла»).
  • Prompt запускается, потому что его выбрал пользователь (как пункт меню или slash-команда).

День 16 — про tools. Инструмент = имя + описание + входная JSON-схема. Модель видит описание и схему, и по ним решает, вызывать ли инструмент и с какими аргументами.

4Транспорты: как байты идут между сторонами

Сервер и клиент могут быть в одном процессе, в разных процессах или на разных машинах.

ТранспортКак работаетКогда использовать
stdioклиент запускает сервер как подпроцесс и пишет JSON-RPC ему в stdin, читает из stdoutлокально, дефолт. наш случай
streamable-httpсервер слушает порт, клиент ходит по URL /mcpдеплой, удалённый сервер
sseстарый HTTP-транспорттолько для старых клиентов новое не строят
Важно

Транспорт не меняет, что сервер умеет. Один и тот же сервер можно запустить и по stdio, и по HTTP — меняется только способ доставки сообщений. Поэтому «подключить MCP» = выбрать транспорт и команду запуска.

Почему для локального примера удобен stdio: не нужны порты, файрвол, внешние сервисы. Клиент стартует сервер как обычный процесс и общается с ним потоком байтов.

5Что происходит на проводе

Под капотом — JSON-RPC 2.0. Полезно увидеть хотя бы раз.

MCP — это JSON-RPC 2.0: клиент шлёт запрос с методом и параметрами, сервер отвечает результатом или ошибкой. Знание этих методов делает «магию» SDK понятной.

1) Рукопожатие — клиент → сервер (initialize)

{"jsonrpc":"2.0","id":1,"method":"initialize",
 "params":{
   "protocolVersion":"2026-07-28",
   "capabilities":{},
   "clientInfo":{"name":"client.py","version":"0.1.0"}
 }}

Сервер → клиент: чем он умеет отвечать (capabilities)

{"jsonrpc":"2.0","id":1,"result":{
   "protocolVersion":"2026-07-28",
   "capabilities":{
     "tools":{"listChanged":true},
     "resources":{"subscribe":true,"listChanged":true},
     "prompts":{"listChanged":true}
   },
   "serverInfo":{"name":"advent-demo","version":"..."}
 }}

2) Список инструментов — клиент вызывает tools/list

{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}

Сервер отвечает массивом инструментов

{"jsonrpc":"2.0","id":2,"result":{"tools":[
   {"name":"add","description":"Add two numbers.",
    "inputSchema":{"type":"object",
      "properties":{"a":{"type":"integer"},"b":{"type":"integer"}},
      "required":["a","b"]}},
   {"name":"echo","description":"Return the given text unchanged.",
    "inputSchema":{"type":"object",
      "properties":{"text":{"type":"string"}},"required":["text"]}},
   {"name":"today","description":"Return today's date in ISO format (YYYY-MM-DD).",
    "inputSchema":{"type":"object","properties":{}}}
]}}

3) Вызов инструмента — клиент вызывает tools/call

{"jsonrpc":"2.0","id":3,"method":"tools/call",
 "params":{"name":"add","arguments":{"a":2,"b":3}}}

// ответ:
{"jsonrpc":"2.0","id":3,"result":{
   "content":[{"type":"text","text":"5"}],
   "structuredContent":{"result":5}
 }}

В коде SDK всё это спрятано. Вот соответствие:

В коде SDKJSON-RPC методЧто делает
async with Client(...)initializeустанавливает соединение и делает рукопожатие
await client.list_tools()tools/listполучает список инструментов
await client.call_tool(name, args)tools/callвыполняет инструмент
Деталь v2

На «проводе» поле называется inputSchema (camelCase), а в Python-объекте к нему обращаются как tool.input_schema (snake_case). То же с output_schema. Не путай имя по протоколу и имя атрибута в Python — именно на этом спотыкается большинство.

6Разбор нашего кода

server.py — объявляем инструменты

from datetime import date
from mcp.server import MCPServer

mcp = MCPServer("advent-demo")          # создаём сервер

@mcp.tool()                             # декоратор регистрирует инструмент
def add(a: int, b: int) -> int:
    """Add two numbers."""              # docstring = описание для модели
    return a + b                        # type hints = входная схема

@mcp.tool()
def echo(text: str) -> str:
    """Return the given text unchanged."""
    return text

@mcp.tool()
def today() -> str:
    """Return today's date in ISO format (YYYY-MM-DD)."""
    return date.today().isoformat()

if __name__ == "__main__":
    mcp.run()                           # без аргумента — транспорт stdio

Заметь, чего мы не писали: ни JSON-схемы, ни парсинга запросов, ни обработки протокола, ни объявления capabilities. Всё выводится из самой функции:

  • имя — из имени функции (add);
  • описание — из docstring («Add two numbers.»);
  • схема аргументов — из аннотаций типов (int → {"type":"integer"}).
Почему if __name__ == "__main__"

Всё, что загружает сервер (тесты, mcp dev, mcp run), сначала импортирует этот файл. Guard не даёт импорту превратиться в запущенный сервер.

client.py — подключаемся и спрашиваем список

import sys
from pathlib import Path
from mcp import Client, StdioServerParameters

SERVER_SCRIPT = Path(__file__).with_name("server.py")

def server_params() -> StdioServerParameters:
    return StdioServerParameters(
        command=sys.executable,            # тот же Python, что и у venv
        args=[str(SERVER_SCRIPT)],         # путь к server.py
    )

async def fetch_tools() -> list:
    async with Client(server_params()) as client:   # вход = запуск подпроцесса
        result = await client.list_tools()          # tools/list
        return result.tools

async def call_add(a: int, b: int):
    async with Client(server_params()) as client:
        return await client.call_tool("add", {"a": a, "b": b})
Тонкость

Конструирование Client(...) ещё не подключается — оно лишь выбирает транспорт. Соединение открывается на входе в async with, а выход из блока выключает подпроцесс. Попытка обратиться к соединению до входа даст ошибку Client must be used within an async context manager.

Тонкость Windows

Используем sys.executable, а не строку "python". На Windows python может оказаться системным интерпретатором без наших пакетов. sys.executable — это абсолютный путь к тому самому python из venv.

test_mcp.py — честная проверка

def test_connection_returns_three_tools():
    tools = asyncio.run(fetch_tools())                 # реальное подключение
    assert sorted(t.name for t in tools) == ["add", "echo", "today"]

Тест не мокает транспорт: он честно поднимает сервер подпроцессом. Так проверяются оба требования задания — «соединение устанавливается» и «список корректно возвращается».

8MCP Inspector — посмотреть глазами

Inspector — графический отладчик серверов. Он делает ровно то, что делает реальный host: запускает твой файл подпроцессом и подключается по stdio, показывая вкладки Tools / Resources / Prompts.

& ".venv\Scripts\python.exe" -m pip install "mcp[cli]"
& ".venv\Scripts\python.exe" -m mcp dev server.py

Inspector — это Node.js-приложение, поэтому нужен npx в PATH. На вкладке Tools ты увидишь нашу форму: обязательные поля a и b — Inspector построил их из type hints.

Зачем это тебе

Когда пишешь свой сервер, Inspector — самый быстрый способ убедиться, что инструменты и схемы выглядят так, как ты ожидаешь, ещё до подключения к настоящему host.

9Как подключить к реальному host

Чтобы твой сервер подхватил настоящий host (Claude Desktop, Cursor, VS Code), host нужно научить команде запуска сервера. Это делается в его config-файле. Общий принцип у всех одинаковый:

Форма записи: имя сервера + команда + аргументы (+ env)

{
  "mcpServers": {
    "advent-demo": {
      "command": "C:\\path\\to\\day16\\.venv\\Scripts\\python.exe",
      "args": ["C:\\path\\to\\day16\\server.py"]
    }
  }
}
Подпроцесс не наследует твоё окружение

Клиент запускает сервер с минимальным allow-list переменных (HOME, PATH и т.п.), чтобы ничего секретного не утекло. Если серверу нужен ключ — передай его явно через env.

{
  "mcpServers": {
    "advent-demo": {
      "command": "python",
      "args": ["server.py"],
      "env": { "MY_API_KEY": "..." }
    }
  }
}

Конкретные имена файлов конфигурации зависят от host'а — их документация скажет точный путь. Но структура одна: command + args + (опц.) env. Никаких «регистраций» и «плагин-маркетплейсов» — просто команда, которой host запускает твой файл.

Совет

Если подключаешь по HTTP вместо stdio, укажи URL (http://127.0.0.1:8000/mcp) вместо команды — host сам поймёт транспорт по типу значения. Но начинать всегда проще со stdio.

10Пишем свои инструменты, ресурсы, промпты

Один декоратор на примитив. Имя, описание и схема берутся из функции.

Инструмент с описанием и ограничениями

from typing import Annotated, Literal
from pydantic import Field

@mcp.tool()
def search(
    query: Annotated[str, Field(description="Что искать.")],
    limit: Annotated[int, Field(ge=1, le=50, description="Максимум результатов.")] = 10,
    genre: Literal["fiction", "poetry"] | None = None,
) -> str:
    """Найти записи по запросу."""
    return f"Нашёл для {query!r} (до {limit})"

Field(description=...) добавляет описание аргумента, ge/le — числовые границы, Literal — перечисление. Если клиент пришлёт limit=999, SDK вернёт ошибку до вызова функции — самоисправляющиеся агенты бесплатно.

Принимать сложный объект

from pydantic import BaseModel, Field

class Book(BaseModel):
    title: str
    year: int = Field(ge=1450)

@mcp.tool()
def add_book(book: Book) -> str:
    """Добавить книгу в каталог."""
    return f"Добавлено: {book.title} ({book.year})"

Схема Book вложится во входную схему инструмента, модель заполнит JSON-объект, а функция получит уже валидированный Book.

Resource — данные для контекста

@mcp.resource("greeting://{name}")
def greeting(name: str) -> str:
    """Поздороваться по имени."""
    return f"Привет, {name}!"

{name} делает это шаблоном ресурса: отдельного ресурса нет, пока не подставят имя.

Prompt — шаблон сообщений

@mcp.prompt()
def summarize(text: str) -> str:
    """Сжать текст до одного предложения."""
    return f"Сожми в одно предложение:\n\n{text}"

Возвращаемая строка становится сообщением пользователя. Вот и весь prompt — функция, которая строит сообщения.

Асинхронный инструмент для I/O

Если инструмент ходит в сеть или читает файл — объяви его async def и используй await. Обычный def тоже работает: SDK выполнит его в отдельном потоке, чтобы не блокировать сервер.

В 2026 pip install mcp ставит v2. У v1 был другой API. Если увидишь пример из интернета и он не работает — скорее всего он для v1.

13Частые вопросы

Нужен ли интернет?

Нет. Наш пример полностью локальный: клиент и сервер — два процесса на твоей машине, сеть не используется.

Нужен ли LLM/API-ключ?

Нет. День 16 — только про соединение и список инструментов. Вызов модели появится, когда будем встраивать MCP в агента.

Почему stdio, а не HTTP?

Локальный сервер проще запускать как подпроцесс: нет портов, ничего не надо освобождать, нечему мешать. HTTP выберем для деплоя.

Это же просто вызов функции — зачем протокол?

Смысл — в совместимости: сервер описывается один раз, и его подхватит любой клиент. Плюс единые правила: capabilities, схемы, валидация, ошибки.

Можно ли вызвать инструмент без модели?

Да — именно это делает наш --call-add и тест. MCP не требует модели для вызова; модель нужна, чтобы решать, какой инструмент вызвать.

15Упражнения (чтобы закрепить)

  1. Добавь инструмент sub(a, b), который вычитает. Проверь, что в client.py он появился в списке, а тест всё ещё зелёный.
  2. Добавь инструмент с необязательным аргументом (значение по умолчанию) и посмотри в выводе, как изменилась input_schema (появится default, уйдёт из required).
  3. Добавь @mcp.resource("greeting://{name}") и запусти mcp dev server.py — найди ресурс во вкладке Resources.
  4. Запусти свой сервер по HTTP: mcp.run(transport="streamable-http", port=3001) и подключись к нему URL-ом вместо StdioServerParameters.
  5. Сломай что-нибудь намеренно: выведи print("hi") в начале server.py и посмотри, что произойдёт с stdio-соединением. (Подсказка: это про «stdout — провод».)
