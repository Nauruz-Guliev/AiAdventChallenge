# Урок: как работает MCP и как настроить его самому

Это отдельный урок к дню 16. Цель — чтобы после него ты мог сам написать
MCP-сервер, подключить к нему клиента и объяснить, что происходит.

## 1. Зачем нужен MCP

Представь: у тебя есть LLM-приложение (чат, IDE, агент). Ты хочешь дать ему
доступ к разным вещам: файлам, базе, Jira, календарю. Без стандарта каждая
интеграция — это свой самодельный протокол: свой способ описать инструмент,
свой формат вызова. Получается N интеграций × M приложений.

MCP решает это одним протоколом: **сервер** один раз описывает свои
возможности по стандарту, и любой **клиент**, который этот протокол понимает,
может их использовать. Аналогия: USB-C. Устройство (сервер) и компьютер
(клиент) договариваются по общему стандарту, а не по уникальному разъёму.

## 2. Три роли

- **host** — LLM-приложение (чат, IDE, агент). То, с чем говорит пользователь.
- **client** — половина host, которая говорит по MCP. На каждый сервер — свой
  клиент внутри host.
- **server** — то, что пишешь ты. Отдаёт инструменты/данные. С моделью напрямую
  не общается.

## 3. Три примитива сервера

Главное отличие — **кто решает использовать**:

| Примитив | Кто управляет | Что это | HTTP-аналогия |
|---|---|---|---|
| **Tools** | модель | функция, которую модель вызывает для действия | `POST` |
| **Resources** | приложение | данные, которые host кладёт модели в контекст | `GET` |
| **Prompts** | пользователь | переиспользуемый шаблон сообщений | «сохранённый запрос» |

День 16 — про **tools**. Инструмент = имя + описание + входная JSON-схема.

## 4. Транспорты: как байты идут между клиентом и сервером

- **stdio** — клиент запускает файл сервера как подпроцесс и пишет JSON-RPC ему
  в stdin, читает из stdout. Локальный вариант, дефолт. **Мы используем его.**
- **Streamable HTTP** — сервер слушает порт, клиент ходит по URL `/mcp`. Для
  деплоя.
- **SSE** — старый HTTP-транспорт, вытеснен Streamable HTTP. Новое не строят.

Важно: транспорт **не меняет, что сервер умеет** — один и тот же сервер можно
отдать и по stdio, и по HTTP.

## 5. Что происходит на проводе

MCP — это **JSON-RPC 2.0**. Когда клиент подключается:

1. **initialize** — рукопожатие: стороны обмениваются версией протокола и
   **capabilities** (какие семейства запросов сервер поддерживает: tools,
   resources, prompts).
2. **tools/list** — клиент просит список инструментов. Сервер отвечает
   массивом: у каждого `name`, `description`, `inputSchema`.
3. **tools/call** — клиент просит выполнить инструмент с аргументами.

В коде SDK всё это спрятано: `client.list_tools()` — это и есть `tools/list`,
`client.call_tool(...)` — `tools/call`.

Важная деталь SDK v2: на «проводе» поле называется `inputSchema` (camelCase),
а в Python-объекте к нему обращаются как `tool.input_schema` (snake_case).
То же с `output_schema`. Не путай имя по протоколу и имя атрибута в Python.

## 6. Разбор нашего кода

### server.py

```python
from mcp.server import MCPServer

mcp = MCPServer("advent-demo")          # создаём сервер

@mcp.tool()                             # декоратор регистрирует инструмент
def add(a: int, b: int) -> int:
    """Add two numbers."""              # docstring = описание для модели
    return a + b                        # type hints = входная схема

if __name__ == "__main__":
    mcp.run()                           # без аргумента — транспорт stdio
```

Заметь, чего мы НЕ писали: ни JSON-схемы, ни парсинга запросов, ни обработки
протокола. Всё выводится из функции: имя — из имени, описание — из docstring,
схема — из аннотаций типов. `int` превращается в `{"type": "integer"}`.

### client.py

```python
from mcp import Client, StdioServerParameters

def server_params():
    return StdioServerParameters(
        command=sys.executable,            # тот же Python, что и у venv
        args=[str(SERVER_SCRIPT)],         # путь к server.py
    )

async def fetch_tools():
    async with Client(server_params()) as client:   # вход = запуск подпроцесса
        result = await client.list_tools()          # tools/list
        return result.tools
```

Тонкость: **конструирование `Client(...)` ещё не подключается** — подключение
происходит на входе в `async with`. Выход из блока выключает подпроцесс.

Тонкость про Windows: используем `sys.executable`, а не `"python"`, чтобы
подпроцесс запускался тем же интерпретатором из venv.

### test_mcp.py

```python
def test_connection_returns_three_tools():
    tools = asyncio.run(fetch_tools())                 # реальное подключение
    assert sorted(t.name for t in tools) == ["add", "echo", "today"]
```

Тест не мокает транспорт: он честно поднимает сервер и проверяет результат. Так
подтверждается, что и соединение, и список инструментов работают.

## 7. Как запустить и посмотреть глазами

```powershell
& ".venv\Scripts\python.exe" client.py            # список инструментов
& ".venv\Scripts\python.exe" client.py --call-add 2 3   # + вызов add
& ".venv\Scripts\python.exe" -m pytest -q         # 3 passed
```

Есть ещё **MCP Inspector** — графический отладчик серверов:

```powershell
& ".venv\Scripts\python.exe" -m pip install "mcp[cli]"
& ".venv\Scripts\python.exe" -m mcp dev server.py
```

Он запускает сервер по stdio и показывает вкладки Tools/Resources/Prompts —
удобно смотреть, что реально видит клиент (нужен `npx` в PATH).

## 8. Как настроить MCP самому (на будущее)

Чтобы твой сервер подхватил реальный host (Claude Desktop, Cursor, VS Code),
host нужно научить команде запуска сервера. Это config-файл host'а, где ты
описываешь: имя сервера + команду. Общий вид (плейсхолдеры — под свой host):

```json
{
  "mcpServers": {
    "advent-demo": {
      "command": "C:\\path\\to\\day16\\.venv\\Scripts\\python.exe",
      "args": ["C:\\path\\to\\day16\\server.py"]
    }
  }
}
```

Если серверу нужны секреты (API-ключи), их передают через `env`, потому что
подпроцесс **не наследует** твоё окружение целиком — только минимальный
allow-list:

```json
{
  "mcpServers": {
    "advent-demo": {
      "command": "python",
      "args": ["server.py"],
      "env": { "MY_API_KEY": "..." }
    }
  }
}
```

Конкретные пути и имена файлов конфигурации зависят от host'а — их документация
скажет точный файл. Принцип один: **команда + аргументы + (опц.) env**.

## 9. Частые ошибки и диагностика

- **Сервер печатает в stdout.** В stdio-режиме stdout — это «провод»: обычный
  `print()` может испортить протокол. Для логов используй `logging` (он идёт в
  stderr).
- **Секреты не доходят.** Подпроцесс получает урезанное окружение. Передавай
  через `env=`.
- **Не тот Python.** На Windows `python` может быть системным. Используй
  `sys.executable` или полный путь к python из venv.
- **Путаница версий.** `pip install mcp` в 2026 ставит SDK **v2** (`MCPServer`,
  `Client`, атрибут `input_schema`). Старый v1 (`FastMCP`, `ClientSession`,
  `inputSchema`) — это другой API. Мы держим `mcp>=2,<3`.

## 10. Что дальше

Мы научились **получать** список инструментов. Следующий шаг для агента —
передать этот список LLM как доступные функции, вызвать выбранный инструмент
(`tools/call`) и вернуть результат модели. Это уже интеграция MCP в агента, а
не минимальный клиент.
