День 17 · MCP

Первый инструмент MCP: погода

День 16 дал протокол MCP: роли, транспорты, JSON-RPC, как поднять клиент и подключить сервер к host. Здесь — следующий шаг: настоящий инструмент вокруг внешнего API, который агент вызывает сам и использует его результат.

Python · mcp v2 · stdio · Open-Meteo geocoding + wttr.in · opencode

1.Задание дня

Реализовать MCP-сервер вокруг любого API и подключить инструмент к агенту, чтобы агент его вызвал:

  • 👉 регистрацию инструмента;
  • 👉 описание входных параметров;
  • 👉 возврат результата;
  • 👉 вызов из приложения и использование результата.

Берём погоду: два инструмента — get_weather и get_forecast. Агент — opencode.

2.Инструмент: регистрация, параметры, результат

Сервер — MCPServer("weather"); инструмент регистрируется декоратором @mcp.tool(), имя берётся из функции. Параметры выводятся из сигнатуры и docstring, результат — это возвращаемый dict. (Механика схемы и протокола — в дне 16; здесь смотрим на конкретный рабочий инструмент.)

day17/server.py

from mcp.server import MCPServer
import weather_api

mcp = MCPServer("weather")

@mcp.tool()
def get_weather(city: str) -> dict:
    """Текущая погода в городе.

    Args:
        city: Название города, например "Москва".
    """
    try:
        place = weather_api.geocode(city)
        current = weather_api.current_weather(place.latitude, place.longitude)
    except weather_api.WeatherError as exc:
        raise ValueError(str(exc)) from exc
    return {"city": place.name, **current}


@mcp.tool()
def get_forecast(city: str, days: int = 3) -> dict:
    """Прогноз погоды на несколько дней (days: 1..3)."""
    days = max(1, min(3, days))
    place = weather_api.geocode(city)
    return {"city": place.name,
            "days": weather_api.daily_forecast(place.latitude, place.longitude, days)}


if __name__ == "__main__":
    mcp.run()   # stdio

day17/weather_api.py

def current_weather(latitude, longitude) -> dict:
    data = _fetch_wttr(latitude, longitude)          # https://wttr.in/lat,lon?format=j1&lang=ru
    current = data["current_condition"][0]
    return {"temperature_c": float(current["temp_C"]),
            "feels_like_c": float(current["FeelsLikeC"]),
            "humidity_percent": int(current["humidity"]),
            "wind_kmh": float(current["windspeedKmph"]),
            "weather": _describe(current)}   # русский из lang_ru
Выбор API

Хост api.open-meteo.com на этой сети заблокирован, а геокодинг Open-Meteo и wttr.in доступны. Поэтому погоду берём у wttr.in, а описания — из поля lang_ru (lang=ru).

HTTP — на стандартном urllib, без лишних зависимостей; ошибки сети/города заворачиваются в WeatherError.

4.Подключение к opencode

Инструмент подхватывает harness — opencode. Ему нужно сказать, как запустить сервер. Конфиг — в корне репозитория (проектный: действует только здесь):

opencode.json (корень репозитория)

{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "weather": {
      "type": "local",
      "command": ["uv", "run", "--no-project",
                  "--with", "mcp>=2,<3", "server.py"],
      "cwd": "day17",
      "enabled": true,
      "timeout": 60000
    }
  }
}
ПолеСмысл
type"local" — opencode сам запускает процесс и говорит по stdio
commandмассив «команда + аргументы»; uv сам подтянет mcp
cwdрабочая папка сервера относительно корня воркспейса
Грабли

Путь должен быть либо относительным корня воркспейса (проектный конфиг), либо абсолютным (глобальный). Относительный путь в глобальном конфиге ломается вне папки проекта: сервер не находит server.py, падает, и в статусе — weather failed / Disabled.

Проверить статус и точную команду:

& opencode mcp list
# ● ✓ weather connected

Конфиг читается один раз при старте — после правки перезапусти opencode.

5.Как агент подхватывает инструмент

Opencode при старте запускает сервер, забирает описание инструментов и отдаёт их модели. Дальше — по запросу:

Пользователь

«какая погода в Москве?»

→

LLM

выбирает инструмент и аргументы

→

Сервер

выполняет, ходит в API

Модель видит не код, а имя, описание и схему аргументов (с префиксом сервера — weather_get_weather). Исполняет инструмент сервер, не модель. Результат возвращается модели, и только потом появляется ответ.

Что происходит в чате

Пользователь:  Какая сейчас погода в Москве?
LLM:           → weather_get_weather({"city": "Москва"})
Сервер:        {"temperature_c": 13.0, "weather": "Пасмурно", ...}
LLM:           В Москве сейчас 13 °C, пасмурно, ветер 8 км/ч.
Итог дня

Агент сам решил, какой инструмент вызвать, передал аргумент city и использовал реальный результат в ответе — полный цикл «запрос → вызов → результат → ответ».
