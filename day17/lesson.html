День 17 · MCP

Первый инструмент MCP: погода

Собираем настоящий MCP-инструмент вокруг внешнего API и подключаем его к агенту: регистрация инструмента, описание входных параметров, возврат результата — и подробно, как MCP настраивается и подключается в opencode и других harness, и как агент подхватывает инструменты.

Python · mcp v2 · stdio · Open-Meteo geocoding + wttr.in · opencode

1.Задание дня

Реализовать свой MCP-сервер вокруг любого API и подключить инструмент к агенту:

  • 👉 регистрацию инструмента;
  • 👉 описание входных параметров;
  • 👉 возврат результата;
  • 👉 вызов из приложения и использование результата.

Берём погоду: два инструмента — get_weather и get_forecast. Агент — opencode.

2.Что такое инструмент MCP

MCP-сервер объявляет агенту инструменты. Инструмент — это функция с именем, описанием, входной схемой и результатом. Агент получает список инструментов и, когда нужно, вызывает один из них.

Агент (harness)

решает, какой инструмент вызвать

→

MCP-сервер

объявляет и выполняет инструменты

→

Внешний API

Open-Meteo + wttr.in

Три роли, которые важно не путать: harness (opencode, Claude Desktop, Cursor — приложение с LLM), MCP-сервер (наш server.py) и LLM (модель, которая выбирает инструмент). Модель сама код не исполняет — исполняет сервер.

3.Регистрация инструмента

Сервер создаётся как MCPServer("weather"), инструмент регистрируется декоратором @mcp.tool(). Имя инструмента — имя функции.

day17/server.py

from mcp.server import MCPServer
import weather_api

mcp = MCPServer("weather")   # имя сервера (ключ подключения)

@mcp.tool()
def get_weather(city: str) -> dict:
    """Текущая погода в городе."""
    ...

if __name__ == "__main__":
    mcp.run()   # stdio-транспорт: читает/пишет JSON-RPC на stdin/stdout

4.Описание параметров

Параметры описываются типизированной сигнатурой и docstring. MCP сам строит из них JSON-схему inputSchema.

day17/server.py

@mcp.tool()
def get_forecast(city: str, days: int = 3) -> dict:
    """Прогноз погоды на несколько дней.

    Args:
        city: Название города, например "Москва".
        days: Число дней прогноза от 1 до 3. По умолчанию 3.
    """
PythonJSON-схема (на проводе)
city: str{"type":"string"}, required: ["city"]
days: int = 3{"type":"integer","default":3}
Ловушка

В Python-объекте поле называется tool.input_schema (snake_case), а на проводе — inputSchema (camelCase).

5.Возврат результата

Возвращаем dict — структурированные данные, а ошибки превращаем в понятные.

day17/server.py

@mcp.tool()
def get_weather(city: str) -> dict:
    try:
        place = weather_api.geocode(city)
        current = weather_api.current_weather(place.latitude, place.longitude)
    except weather_api.WeatherError as exc:
        raise ValueError(str(exc)) from exc
    return {"city": place.name,
            "temperature_c": current["temperature_c"],
            "weather": current["weather"], ...}

Ответ на tools/call

{
  "content": [{ "type": "text",
    "text": "{\"city\":\"Москва\",\"temperature_c\":13.0,\"weather\":\"Пасмурно\"}" }],
  "isError": false
}
Что видит агент

Результат-dict сериализуется в JSON и кладётся в content[0].text; агент читает его и использует в ответе.

day17/weather_api.py

def current_weather(latitude, longitude) -> dict:
    data = _fetch_wttr(latitude, longitude)          # https://wttr.in/lat,lon?format=j1&lang=ru
    current = data["current_condition"][0]
    return {"temperature_c": float(current["temp_C"]),
            "feels_like_c": float(current["FeelsLikeC"]),
            "humidity_percent": int(current["humidity"]),
            "wind_kmh": float(current["windspeedKmph"]),
            "weather": _describe(current)}   # русский из lang_ru
Выбор API

Хост api.open-meteo.com на этой сети заблокирован, а геокодинг Open-Meteo и wttr.in доступны. Поэтому погоду берём у wttr.in, а описания — из поля lang_ru (параметр lang=ru).

7.Настройка MCP в harness

MCP-сервер — это процесс, с которым harness общается по stdio (или по сети). Harness'у нужно знать всего две вещи: как его зовут и как его запустить. Это описывается в конфиге harness'а.

7.1Где лежит конфиг (opencode)

opencode ищет проектный конфиг, поднимаясь от рабочей папки вверх до корня воркспейса; глобальный конфиг читается всегда. Слои глубоко сливаются, проект перекрывает глобальное.

ОбластьПутьГде действует
Проект./opencode.json, ./opencode.jsonc или .opencode/opencode.jsonтолько этот проект
Глобально~/.config/opencode/opencode.jsonвсе проекты
Правило

Файл в корне воркспейса — не в подпапке. Из day17/opencode.json он не подхватится: opencode идёт вверх от рабочей папки, а не вниз.

7.2Блок mcp

Каждый сервер — ключ в объекте mcp. Ключ и есть имя сервера (оно попадёт в имена инструментов).

opencode.json (проектный, в корне репозитория)

{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "weather": {                       // ← имя сервера
      "type": "local",               // запуск локального процесса; бывает "remote"
      "command": ["uv", "run", "--no-project",
                  "--with", "mcp>=2,<3", "server.py"],
      "cwd": "day17",                  // относителен корня воркспейса
      "enabled": true,
      "timeout": 60000                 // мс на получение списка инструментов
    }
  }
}
ПолеОбязательноСмысл
typeда"local" (stdio-процесс) или "remote" (url)
commandда (local)массив: исполняемый файл + аргументы
cwdнетрабочая папка процесса; относительна корня воркспейса
environmentнетпеременные окружения для сервера
enabledнетfalse — выключить сервер
timeoutнеттаймаут (мс) на tools/list, по умолчанию 5000

Удалённый сервер (по URL) — так:

"remote-thing": {
  "type": "remote",
  "url": "https://mcp.example.com/mcp",
  "headers": { "Authorization": "Bearer {env:MY_TOKEN}" }
}

7.3Проектное или глобальное?

  • Проектное (рекомендуется для репозитория): конфиг в корне репо, относительные пути работают, у других проектов MCP нет. Легко коммитить.
  • Глобальное: сервер доступен везде, но относительным путям доверять нельзя — процесс может стартовать из любой папки. В глобальном конфиге используй абсолютные пути и к команде, и к серверу.
Реальный баг этого дня

В глобальном конфиге стояло --directory day17 (относительный путь). Из корня репо — ✓ connected, из любой другой папки — ✗ weather failed (MCP error -32000: Connection closed): процесс не находил day17 и сразу завершался.

Лечение: абсолютный путь к серверу (или абсолютный cwd).

7.4Перезапуск обязателен

Конфиг читается один раз при старте harness. После правки — закрыть и заново открыть приложение (и терминал, если менялась переменная окружения), иначе изменения не подхватятся.

9.Как агент подхватывает инструменты

Это последовательность, которую harness проходит при старте и в каждый вызов.

  1. Старт harness. Он читает конфиг и для каждого local MCP запускает процесс (command + cwd).
  2. Handshake. Клиент шлёт initialize (версия протокола, свои capabilities). Сервер отвечает serverInfo и своими capabilities.
  3. Список инструментов. Harness запрашивает tools/list и получает имя, описание и inputSchema каждого инструмента.
  4. Инструменты попадают в контекст модели. Harness добавляет их как доступные функции. Имена префиксуются именем сервера: weather_get_weather, weather_get_forecast.
  5. Запрос пользователя. Модель видит вопрос и список инструментов и решает, что нужен weather_get_weather с аргументом city.
  6. Вызов. Harness отправляет tools/call с именем и аргументами — исполняет не модель, а сервер.
  7. Результат. Сервер выполняет функцию (geocode + wttr.in) и возвращает content (и/или structuredContent).
  8. Ответ. Harness возвращает результат модели; модель формулирует финальный ответ, уже опираясь на реальные данные.

Пользователь

«погода в Москве?»

→

LLM

выбирает инструмент и аргументы

→

MCP-сервер

выполняет, ходит в API

И обратно: результат уходит в контекст модели, и только потом появляется ответ. Цикл «модель → вызов → результат → модель» может повторяться несколько раз за один запрос, если инструментов несколько.

9.1Что именно «видит» модель

Не код, а описание инструмента: имя, человекочитаемое описание и JSON-схему аргументов. Поэтому важно писать понятные docstring'и — по ним модель решает, когда звать инструмент и какие аргументы передать.

// так harness показывает инструмент модели
weather_get_weather(city: string)          // обязательный
  "Текущая погода в городе."

weather_get_forecast(city: string, days: integer = 3)
  "Прогноз погоды на несколько дней."

9.2Три следствия

  • Инструменты стоят контекста. Каждый сервер добавляет свои описания в промпт — не подключай десятки серверов «на всякий случай».
  • Изоляция. Сервер не знает про модель и harness: его можно подключить к opencode, Cursor, Claude Desktop без изменений.
  • Права. Harness может спросить разрешение на вызов или запретить часть инструментов — это уже политика harness, а не MCP.

10.JSON-RPC на проводе

Внутри stdio — обычные JSON-RPC-сообщения. Вот суть (упрощённо).

1. Handshake (opencode → сервер)

{"jsonrpc":"2.0","id":0,"method":"initialize",
 "params":{"protocolVersion":"...","capabilities":{},"clientInfo":{"name":"opencode"}}}

2. Список инструментов (opencode → сервер)

{"jsonrpc":"2.0","id":1,"method":"tools/list"}

сервер → opencode (сокращённо)

{"jsonrpc":"2.0","id":1,"result":{"tools":[
  {"name":"get_weather",
   "description":"Текущая погода в городе.",
   "inputSchema":{"type":"object",
     "properties":{"city":{"type":"string"}},"required":["city"]}},
  {"name":"get_forecast",
   "inputSchema":{"type":"object",
     "properties":{"city":{"type":"string"},
       "days":{"type":"integer","default":3}},"required":["city"]}}
]}}

3. Вызов (opencode → сервер)

{"jsonrpc":"2.0","id":2,"method":"tools/call",
 "params":{"name":"get_weather","arguments":{"city":"Москва"}}}

4. Результат (сервер → opencode)

{"jsonrpc":"2.0","id":2,"result":{
  "content":[{"type":"text",
    "text":"{\"city\":\"Москва\",\"temperature_c\":13.0,\"weather\":\"Пасмурно\"}"}],
  "isError":false}}

11.Отладка подключения

Проверить статус всех серверов и точную команду, которой они запускаются:

& opencode mcp list
# ● ✓ weather connected
#      uv run --no-project --with mcp>=2,<3 server.py

Если сервер не поднялся, opencode печатает failed, а в лог попадает server unavailable … status=failed. Лог: ~/.local/share/opencode/log/opencode.log.

СимптомПричинаЧто делать
failed / Disabledпроцесс не стартовалпроверить команду вручную; пути, PATH, таймаут, импорты
Работает из корня, падает внеотносительный путь в глобальном конфигеабсолютные пути
Конфиг «не виден»файл лежит в подпапкеположить в корень воркспейса
Не подхватились правкиконфиг читается один разперезапустить harness

Ручная проверка того же stdio-канала — нашим клиентом из дня 16 или простым Python-скриптом с Client(...): запустить сервер, попросить tools/list и вызвать инструмент. Если так работает — проблема в конфиге harness, а не в сервере.

Полезные переменные opencode

OPENCODE_CONFIG — загрузить дополнительный конфиг из файла; OPENCODE_CONFIG_CONTENT — вставить конфиг строкой; OPENCODE_DISABLE_PROJECT_CONFIG=1 — не читать проектный конфиг (аварийный запуск).

12.Тесты

15 офлайн-тестов: API мокается, поэтому сеть не нужна. Интеграционный тест поднимает сервер по stdio и проверяет список инструментов и схемы.

& ".venv\Scripts\python.exe" -m pytest -q
# 15 passed
  • _describe — русский текст / фолбэк;
  • geocode — координаты / город не найден / ошибка;
  • current_weather, daily_forecast — форма / пустой ответ;
  • get_weather, get_forecast — форма, clamp days, ValueError;
  • stdio — 2 инструмента, схема city обязателен, days по умолчанию 3.

13.Упражнения

  1. Инструмент get_temperature(city) — только температура.
  2. Параметр units (metric/imperial).
  3. Ограничь days через Literal[1,2,3] и посмотри новую схему.
  4. Инструмент compare(cities: list[str]) — сравнить погоду в городах.
  5. Подключи тот же сервер к Cursor или Claude Desktop по примерам из раздела 8 — убедись, что код сервера не меняется.
