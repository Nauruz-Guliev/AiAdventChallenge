# День 13: состояние задачи (конечный автомат)

Самостоятельное продолжение `day12`. Поверх агента с профилем и памятью добавлено
**формализованное состояние задачи**: этап, текущий шаг и ожидаемое действие.
Агент ведёт задачу через этапы `planning → execution → validation → done`, задача
можно поставить на паузу в любой момент и продолжить **без повторных объяснений**.

`day6`–`day12` не изменяются.

## Что изучаем

Раньше агент отвечал на каждое сообщение «с нуля», и было непонятно, на каком
месте длинной задачи он находится. День 13 вводит конечный автомат: состояние
задачи хранится явно, переходы детерминированы, а поле «ожидаемое действие»
показывает, что должно произойти дальше.

| этап | смысл | ожидаемое действие |
| --- | --- | --- |
| `planning` | агент разбирает задачу | агент составляет план |
| `execution` | агент выполняет план по шагам | агент выполняет шаг X |
| `validation` | агент проверяет результат | агент проверяет результат |
| `done` | задача завершена | новая задача от пользователя |

Переходы только вперёд; пауза — ортогональный флаг и работает на любом этапе
кроме `done`.

## Как это устроено

1. Первое сообщение пользователя создаёт задачу и переводит автомат в `planning`.
2. Агент отвечает планом: строго JSON-массив шагов в блоке ` ```json … ``` `.
   Бэкенд парсит план, сохраняет шаги и переводит автомат в `execution`, шаг 1/N.
3. Каждый следующий ответ агента — ровно один шаг. Номер шага увеличивается,
   после последнего автомат переходит в `validation`.
4. Ответ на этапе `validation` — отчёт проверки, после него автомат переходит в
   `done`.
5. Если план не распознан, делается одна автопопытка с подсказкой о формате;
   состояние при этом не портится.

Ключевое решение: **переходы двигает бэкенд, а не LLM**. Модель поставляет
контент (план, шаги, отчёт), а таблица переходов живёт в коде и покрыта тестами —
демонстрация не «флакает» на забытых или двойных переходах.

## Пауза и продолжение

- «⏸ Пауза» на панели — на любом этапе.
- Пока задача на паузе, агент отвечает «задача на паузе» и **не вызывает модель**.
- «▶ Продолжить» возвращает тот же этап и шаг; история диалога сохраняется, а в
  промпт добавляется «не повторяй план и предыдущие объяснения».
- Состояние лежит в `data/task_state.json` — переживает перезапуск бэкенда и
  перезагрузку страницы.

## Ручной ритуал проверки

1. Пустой чат: панели «Состояние задачи» нет.
2. Отправьте «Напиши функцию…» — появляется панель: этап «планирование».
3. Агент отвечает планом — этап становится «выполнение», шаг 1/N, виден текст шага.
4. **Пауза** на шаге 2 → бейдж «на паузе», отправьте сообщение — агент отвечает,
   что задача на паузе, и модель не вызывается.
5. **Продолжить** → следующее сообщение двигает тот же шаг, агент не повторяет
   план.
6. Пройдите шаги до конца → «проверка» → «готово».

## Запуск

```powershell
# backend (Windows)
cd day13\backend
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
# .env: DEEPSEEK_API_KEY=... (см. .env.example)
.venv\Scripts\python -m uvicorn app.main:app --reload
```

```powershell
# frontend — во втором терминале
cd day13\frontend
npm install
npm run dev   # http://localhost:5173
```

Если `day12` держит порт 8000/5173 — сначала остановите его.

## API

- `GET /api/task/state` → состояние автомата (этап, шаг, ожидаемое действие, пауза);
- `POST /api/task/pause` · `POST /api/task/resume`;
- `POST /api/chats/{id}/messages` возвращает поле `task` с новым состоянием;
  на паузе отвечает уведомлением без вызова модели;
- остальные эндпоинты — как в `day12`.

## Честные ограничения

- Модель может вернуть шаг в свободной форме — контент не валидируется, только
  план (структура JSON).
- Автопопытка парсинга плана тратит один дополнительный запрос к модели.
- Состояние одно на приложение (одна активная задача), мультизадачности нет.
- Переходы линейные: вернуться на предыдущий этап нельзя.

## Структура

- `app/domain/task_state.py` — `Stage`, `TaskState`, таблица переходов, «ожидаемое действие»;
- `app/application/task_engine.py` — парсинг плана и промпт-блок состояния;
- `app/application/agent.py` — продвижение автомата после ответа модели;
- `app/application/ports/task_repository.py` · `app/infrastructure/json_task_repository.py` — хранилище `task_state.json`;
- `app/presentation/routes.py` — эндпоинты состояния, паузы и продолжения;
- `frontend/src/components/TaskStatePanel.jsx` — степпер этапов, шаг, ожидаемое действие.
