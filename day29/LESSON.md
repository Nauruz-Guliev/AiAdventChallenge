# День 29 — оптимизация локальной LLM (урок)

Задача дня — взять работающую локальную RAG-систему (день 28) и **настроить модель под
конкретный кейс**: ответы по базе Kotlin Multiplatform. Оптимизируем генерацию: параметры,
квантование, prompt-шаблон. Поиск оставляем неизменным, чтобы честно измерить вклад оптимизации.

## 1. Почему именно параметры и промпт

При temperature 1.0 и без лимита длины «думающая» 12B-модель на RAG-контексте часто:

- пишет длинные вступления и повторяет вопрос;
- отвечает «в общем», не опираясь строго на контекст;
- тратит токены впустую (медленнее ответ).

Для справочного RAG нужен **точный, короткий, привязанный к источникам** ответ. Это даёт связка:
низкая temperature + лимит длины + строгий промпт.

## 2. Параметры инференса

| Параметр | Зачем | Наше значение |
|---|---|---|
| `temperature` | меньше — меньше «творчества», стабильнее факты | 0.2 |
| `top_p` / `top_k` | сузить выбор токенов | 0.9 / 40 |
| `num_predict` | лимит длины ответа (скорость + дисциплина) | 512 |
| `num_ctx` | окно контекста: меньше — меньше KV-память | 4096 (с авто-подъёмом) |
| `repeat_penalty` | меньше повторов | 1.1 |
| `think` | «размышления» тратят время | false |

Важно: `num_ctx` не должен быть меньше, чем `промпт + num_predict`, иначе Ollama обрежет
контекст. Наш раннер оценивает длину промпта и при необходимости поднимает окно до 6144.

## 3. Квантование

Один и тот же вес модели можно хранить с разной точностью:

- **Q4_K_M** — 4 бита, ~8 ГБ, быстрее, чуть менее точно;
- **Q8_0** — 8 бит, ~13 ГБ, точнее, но медленнее и заметно больше по памяти.

Сравнение Q4 и Q8 показывает **плату за точность**: где проходит граница «качество/ресурсы» для
нашей задачи. Часто для RAG разница в качестве мала, а цена в памяти — большая.

## 4. Prompt-шаблон

Базовый промпт просил ссылки `[n]` и честность. Оптимизированный добавляет **формат**:

> 1) Кратко: 2–5 пунктов или короткий абзац, без вступлений и повторения вопроса…
> 4) Если ответа в контексте нет — ответь ровно: «Не нашёл в базе».

Это уменьшает длину и «воду», делает ответ предсказуемым и привязывает его к источникам.

## 5. Как читать метрики

- **Качество (0…1)** — средняя оценка слепого судьи. Судья — это LLM (DeepSeek), задание —
  сравнить ответ с эталоном; он не знает, какая модель/профиль/квант отвечали, поэтому не
  подыгрывает «своим».
- **Скорость** — латентность (общее время) и **tok/s** (чистая скорость генерации Ollama).
- **Ресурсы** — размер модели, память (`size_vram` + RSS процесса Ollama), CPU%, время загрузки.
- **Стабильность** — разброс (σ) по прогонам; поэтому в полном режиме 2 прогона на вопрос.

## 6. Что ожидать

- `params` обычно резко снижает латентность (лимит длины + меньше контекста) при том же качестве.
- `optimized` добавляет к этому дисциплину ответа (короче, структурнее) — качество судьи растёт.
- `Q8_0` может дать +ε к качеству и −к скорости/памяти; для RAG это часто невыгодный размен.

## 7. Почему вывод починили

Telegram HTML поддерживает лишь ограниченный набор тегов и **не** понимает `<p>`/`<br>`. Старый
конвертер их добавлял, поэтому `parse_mode="HTML"` падал и сообщение оставалось сырым markdown.
Теперь конвертер выдаёт только поддерживаемые теги и валидный HTML, стриминг рендерит его на
каждом шаге, а таблицы отчётов выводятся как моноширинные `<pre>`-блоки.
