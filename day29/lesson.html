День 29 — оптимизация локальной LLM под RAG

Разбор «сделай сам»: параметры, квантование, prompt-шаблон и честное сравнение до/после.

Идея

Берём рабочую локальную RAG-систему (день 28) и настраиваем модель под конкретный кейс — ответы по базе Kotlin Multiplatform. Меняем только генерацию: параметры инференса, квант модели и prompt-шаблон. Поиск не трогаем.

Кванты: Q4_K_M (gemma4:12b) и Q8_0 (gemma4:12b-it-q8_0).

Шаги, чтобы повторить

  1. Скачай квант: ollama pull gemma4:12b-it-q8_0 (~13 ГБ).
  2. cd day29/backend → venv → pip install -r requirements.txt (при ошибке сертификата — --trusted-host pypi.org --trusted-host files.pythonhosted.org).
  3. copy .env.example .env, вписать TELEGRAM_BOT_TOKEN и DEEPSEEK_API_KEY (для судьи).
  4. Останови день 28 (токен один): day28\backend\stop_bot.ps1.
  5. Запусти: .\run_bot.ps1 — в логе видно, какие кванты есть.
  6. В Telegram: задай вопрос, затем /profile baseline и задай снова — сравни.
  7. /quant q8 — переключи квант; /quant q4 — назад.
  8. /ab (быстро) и /ab full (полно) — таблица качества/скорости/ресурсов.

Как считается сравнение

Матрица 3 профиля × 2 кванта. Retrieval выполняется один раз на вопрос и подаётся всем конфигурациям — сравнивается генерация. Качество оценивает слепой судья (DeepSeek): он видит только вопрос, эталон и ответ, без подписи модели.

Метрики

  • Качество — оценка судьи 0…1 (и σ по прогонам).
  • Скорость — латентность (мс) и tok/s из Ollama.
  • Ресурсы — размер модели, память (/api/ps + RSS процесса Ollama), CPU%, время загрузки.

Фикс вывода в Telegram

Telegram HTML не поддерживает <p> и <br>. Старый конвертер их добавлял → parse_mode="HTML" падал → markdown показывался сырым. Теперь конвертер выдаёт только поддерживаемые теги, стриминг рендерит HTML, таблицы — в <pre>. Тот же фикс есть и в дне 28.
